# `agent` — In-computer AI coding agent over HTTP

## Purpose

The `agent` kit exposes the in-computer AI agent as a typed namespace: create a chat session, send a prompt, stream the turn (tool calls, gates, output), then confirm/answer/cancel as the agent works. services — `sessions` (with `sessions.turns`), `bots`, `definitions`, `models`, `providers`, `skills` (with `skills.hub`), `memory`, `github`, `workflows`, `tools`, `hooks`, `mcp`, `settings`, `loops`, `logs` (with `hoody agent logs export`), `jobs`, `gates`, `changes`, `headless`, `todos`, `usage` (usage statistics), plus the namespace's own calls (`whoami`, the `login` token bootstrap, `pause` and `resume`). Session tasks live under `sessions.tasks`.

## When to use

- **Drive the agent programmatically** — create a session, prompt it, and consume the turn: `hoody agent sessions create` → stream the turn for live tool/gate/output events (per surface — see the streaming note under Quirks), or `hoody agent sessions turns run` for one blocking call → resolve gates with `hoody agent gates approve` / `hoody agent gates deny` / `hoody agent gates answer` → `hoody agent sessions turns cancel` to interrupt.
- **Inspect or configure the agent** — list `models` (`hoody agent models list` / `hoody agent models get`; the Jev decision-model catalogue is the separate `hoody agent jev models list`) and `hoody agent providers list` (configure providers via `hoody agent providers auth default set` / `hoody agent providers apikey set` / `hoody agent providers oauth start`); switch a session's active model with `hoody agent sessions model set`, browse/install `skills`, read/edit `memory`, manage `workflows`, `hooks`, `definitions` (named agent profiles), and `tools` — both the sessionless catalogue/registry (`hoody agent tools list` / `hoody agent tools readonly list` / `hoody agent tools get`, and `hoody agent tools run` (blocks, returns the result; `hoody agent tools run --stream` returns the one-shot result over SSE frames instead, not a per-token stream) / `hoody agent tools start` (returns `{ job_id }`, poll `jobs`) to invoke a tool with no session — read-only by default, a mutating tool needs `allow_mutations: true` or a confirmed re-issue) and the per-session surface (`hoody agent sessions tools list` for a session's *effective* tool set, `hoody agent sessions tools mcp list`, and `hoody agent sessions tools run`). Unlike the sessionless `hoody agent tools run`, a per-session run executes against the session's *frozen* realm/computer/cwd/tool-mode and claims the session's single serial turn slot — so it returns 409 `turn_in_flight` while a turn is running, 409 `gate_parked` while a gate is open, and 404 `tool_not_found` if the tool is not in that session's effective list; whether a mutating tool may run is decided by the live session's own tool mode and confirmation settings (the `allow_mutations` escape hatch is sessionless-only).
- **One-shot non-interactive runs** — a headless run (`POST /api/v1/agent/headless/runs`) runs the full agent loop once over a throwaway session (see workflow 7 for the per-surface form: an async job or an SSE stream).
- **GitHub from inside the agent** — first establish an account with `hoody agent github auth start` (a GitHub device flow → poll `hoody agent github auth poll`) or `hoody agent github auth login --github-token <token>` (a PAT, persisted directly), then `hoody agent github auth status` to confirm; once an account is active, `hoody agent github repos clone` / `hoody agent github commits create` (and `hoody agent github status` / `hoody agent github branches list` / `hoody agent github repos list` / `hoody agent github prs create` / `hoody agent github sync`) for repo operations the agent performs in-computer.

## When NOT to use

- Want an interactive UI, not the API? The agent's own TUI opens at its `agent-1` URL or a terminal link with `agent=true`; in a terminal, `hoody hub` opens the Hub. This namespace is the HTTP control surface beside them.
- Raw shell / command exec → `terminal` (PTY) or `exec` (one-shot). File I/O → `files`. The agent runs these as tools internally; call them directly when you don't need the LLM.
- Account-level resources (computers, billing, realms) → `api`.

## Prerequisites

- Computer with the `agent` kit running; capability URL.
- At least one usable model provider before prompting: one with a stored API key, a stored OAuth login, or passwordless access (the shipped default agent is pinned to a passwordless model). `hoody agent providers list` and `hoody agent models list` list the CATALOGUE, which is populated whether or not anything is configured; `hoody agent providers auth status` reports whether a provider is actually usable (`ready`, with `api_key_stored`, `oauth_stored` and `no_auth_ready` behind it).
- A session id from `hoody agent sessions create` for every prompt/gate/cancel call.

## Capability URL

→ See `SKILL-CLI.md § Proxy URLs`.

**Reaching a service you host on a computer port** (any port, any namespace):

- `https://{projectId}-{computerId}-http-<port>.{node}.computers.hoody.com` — proxy speaks HTTP to `<port>` on the computer's network address. Bind `0.0.0.0:<port>`, which always works; a loopback-only listener is also reached on default computers.
- `https://{projectId}-{computerId}-https-<port>.{node}.computers.hoody.com` — proxy speaks HTTPS to `<port>` on the computer's network address (target needs TLS, bound to `0.0.0.0:<port>` too).

Edge is always `https://`. No alias, firewall edit, or proxy registration needed; capability-token gates still apply.

## Common workflows

### 1. Prompt a session and stream the turn

`hoody agent sessions create` (returns a session id) → stream the turn with `{ text }` to receive live events (tool calls, gates, output deltas) — see the streaming note under Quirks for the supported per-surface method (SDK helper / HTTP SSE route / CLI command) → resolve any gate as it arrives → turn ends.

### 2. One-shot synchronous prompt

`hoody agent sessions create` → `hoody agent sessions turns run` with `{ text }` — waits for the turn to end, a gate that needs a person, or the server deadline (290 seconds by default). A clean turn returns `{status:"done", session_id, turn_id}` with no reply text; check `status`, because a failed, cancelled or quit turn answers `error` (with the error `event`), `canceled` or `quit`. A turn that parks on a gate returns `{pending_gate, turn_id}`. When the deadline passes first the answer is `503 service_unavailable` with `details.turn_id` and `details.turn_running: true`: the turn is NOT cancelled, so follow it with `hoody agent sessions turns get` (or the stream) instead of prompting again. Read the reply with `hoody agent sessions transcript get`. Best for short, non-interactive prompts where you don't need streamed events.

### 3. Resolve gates mid-turn

While a prompt streams, the agent may pause for human input: a confirmation gate → `hoody agent gates approve` / `hoody agent gates deny`; an open question → `hoody agent gates answer` (to get a helper model to DRAFT an answer for a parked question call `hoody agent gates suggest` — it does NOT answer the gate and needs a parked lead question gate (otherwise `409 no_pending_gate`; a helper's gate does not count): it dispatches an async job (HTTP 202) whose suggestion arrives via `hoody agent jobs result get` and an `event.question_suggestion` on the session stream — only one assist may be in flight per session — and the real answer still goes through `hoody agent gates answer`; for unattended runs arm `hoody agent sessions autoreply update` (a self-driving auto-user loop that answers questions only during its own rounds, so arming it does not resolve a question an ordinary prompt already parked: answer that with `hoody agent gates answer`; it also withholds write-class actions unless you opt in with `allow_writes: true`, either on the arm call or later via `hoody agent sessions autoreply writes enable`)). The gate identity to echo is the ENVELOPE-level `gate {id, generation, type}` that the stream frame parking the gate carries beside `seq` / `incarnation` / `event`. The `event.confirm_request` payload also has a numeric `gate_id`, but that is the daemon's id space and is never the value to echo. The answer body for a question gate: the envelope's gate id as `gate_id` (optionally its `generation`), then **answer** (or **text**, used when **answer** is blank) for a single question; for a batch (`event.user_question` carrying `questions[]`), `answers` maps each `questions[].id` to its answer text, for example `{"gate_id":"<gate.id>","answers":{"<questions[].id>":"yes"}}`. A body with no `answer`, no `text` and no `answers` is `400 bad_request` and the question stays parked. The `question_id` on `event.user_question` is a diagnostic number, not a body field. Echoing a wrong/stale `gate_id`/`generation`, or answering when nothing is parked, returns 409 (`no_pending_gate` / `stale_gate` / `gate_already_answered` / `gate_type_mismatch`). A retry of a question answer that names the gate just resolved with the same answer (a lost 200) gets `200` with `replayed: true` and the original acknowledgement, while another answer to that gate is `409 gate_already_answered`. For `hoody agent gates approve` / `hoody agent gates deny`, a decision naming a gate that already ended is `409 gate_already_resolved` (with its recorded outcome), and one naming a gate whose decision is still being applied is `409 gate_decision_pending`: retry naming the gate to learn the outcome. On a session whose approval policy is `always` and whose approver lease was ever minted (`hoody agent sessions approverlease claim`, or the lease handed back by a create or attach that asserted `always`), EVERY decision — `hoody agent gates approve` / `hoody agent gates deny`, and the confirmed re-issue of a gated `hoody agent sessions tools run` — must carry the current lease capability in the `X-Hoody-Approver-Lease` request header. (CLI: `--approver-lease`.) Without it the decision is refused `409 approver_lease_required`, a capability that does not verify is `409 approver_lease_invalid`, and an expired one is `approver_lease_expired` until a holder acquires again. Interrupt a running turn with `hoody agent sessions turns cancel`. Tear the session down: `hoody agent sessions close` removes it from the live map; `hoody agent sessions delete --id <id>` always erases the persisted record too (the CLI has no keep-the-record form; re-attach with `hoody agent sessions create --attach-session-id <id>` works only after `sessions close`). To roll a session back without tearing it down, `hoody agent sessions trim` with `{ turn_idx }` truncates conversation history to (and including) that turn index.

### 4. Pick a model / provider

`hoody agent providers list` to list the catalogued providers (and `hoody agent providers auth status` to check that one is `ready`: a stored credential or passwordless access), `hoody agent models list` to list the catalogued models, then `hoody agent sessions model set` to bind a model to a session before prompting — SYNCHRONOUS: the response reports the actual outcome ({status:'ok', model, persisted} on success; structured 409/422 errors while busy or for an unconstructable spec). For a native session, the default `scope: "agent"` switches the session and TRIES to rewrite the `model:` line of the chat agent's highest-precedence on-disk file (project before home; an embedded-only agent in a scoped realm gets a new copy in that realm's profile layer). That pin applies to later sessions resolving that file: it is per profile layer, not global. That save is best-effort, so only `persisted: true` confirms the repin — `persisted: false` means the session switched but future sessions keep the old pin. With `scope: "session"` (`--scope session`), the switch affects only this session and leaves the agent file alone; `persisted` then says whether the session record was saved. A Claude Code (delegated) session's switch is always session-scoped, takes a Claude alias or model id, and applies from its next turn; it does not rewrite an agent file. PRECEDENCE: the agent's frontmatter `model` is the DEFAULT for a session that does not request one; an explicit model on create (`hoody agent sessions create --model <spec>`), or this live `hoody agent sessions model set`, OVERRIDES that pin for the session — create is session-scoped and does not rewrite the agent, for a native session, this live switch repins the agent file it resolves with the default scope (see above). The shipped default agent ships pinned, so its pin is the out-of-the-box default until an explicit model is chosen (an explicit model together with `attach` is rejected 400, because a resumed session keeps its model; with `backend: "acp"` the model is the Claude Code model: a Claude alias such as `opus`, `sonnet` or `haiku`, or a Claude model id. Any other model is `422 model_unavailable` with `details.reason: not_claude`). Each session has further per-session knobs (all session-scoped PATCHes; while a gate is parked, `hoody agent sessions effort set` and `hoody agent sessions agent set` answer 200 with `deferred: true`, and the change is dropped, not queued: send it again once the turn has ended): `hoody agent sessions effort set` (`{ effort }` — `low|medium|high|xhigh|max`, or `""` for the model default), `hoody agent sessions verbosity set` (`{ level }` — `normal|concise|terse|minimal`), `hoody agent sessions hoodyenv enable` / `hoody agent sessions hoodyenv disable` (turn injection of the `HOODY_*` shell-env contract for the bash tool on or off), and `hoody agent sessions agent set` (`{ agent }` — bind a named profile from `definitions` (`hoody agent definitions list`); `bot`, `script-writer` and `github-installer` are refused `400 bad_request` (a Bot runs `bot`, and the other two are fixed at session start: a session started on one cannot switch away)).

To use a model from an endpoint that is not in the catalogue (anything that speaks the OpenAI Chat Completions, OpenAI Responses or Anthropic Messages API from a public HTTPS address, such as a model server you run yourself or a company gateway), add it as a **custom provider** first. `hoody agent providers create` takes `--id`, `--endpoint` (the base URL) and one `--models model=<name>` per model, then `hoody agent providers apikey set --id <id> --api-key <key>` stores its key (a key never goes in the create command), and its models are `<model_prefix>/<model>` wherever a model is chosen: `hoody agent sessions create --model <spec>`. `hoody agent providers update` changes it and `hoody agent providers delete` removes it; `api_key_removed` in the result says whether its stored key was removed too. The change applies at once, with no restart: new sessions, model switches and Jev see it, and an open session on one of its models picks it up before its next turn. `id` is 1-40 lowercase letters, digits or inner hyphens and cannot change later; `model_prefix` is the `id` unless given, and must equal it; `wire_format` is `chat_completions` (default), `responses` or `messages`, and `auth_scheme` follows it (`bearer`, or `x-api-key` for `messages`). Built-in providers refuse update and delete (`409 provider_builtin`), as does a provider defined in a project's providers file (`409 provider_not_managed`). See Examples for the full run.

### 5. Skills, memory, todos, workflows, agents

- **Skills** — `hoody agent skills list` (each carries an enabled + trust state), `hoody agent skills hub install` / `hoody agent skills hub search` / `hoody agent skills hub preview` to find and install from the hub. A newly installed/imported skill must be trusted before its code runs — `hoody agent skills trust` is the gate (identify the skill by `root_dir`+`rel_dir`; `hoody agent skills untrust` takes the trust back); `hoody agent skills enable` / `hoody agent skills disable` enable or disable by `name`. Both `hoody agent skills trust` (which grants arbitrary code-execution trust) and `hoody agent skills hub install` (which writes arbitrary skill code to disk) take effect immediately over this namespace: there is no confirmation step, and no privilege beyond ordinary access to the kit is required, so an autonomous caller can silently trust and install skill code. Add your own confirmation before exposing these to one.
- **Memory** — `hoody agent memory search` for hybrid recall (BM25 + vector + graph) and `hoody agent memory items list` to enumerate by `project`; `hoody agent memory items create` / `hoody agent memory items update` / `hoody agent memory items delete` to write; `hoody agent memory graph get` for the relation graph (or `hoody agent memory items get` to read one record by `id`). `hoody agent memory enable` / `hoody agent memory disable` are the memory capture/privacy switch — they persist `features.memory` and flip the live store — and `hoody agent memory flush` forces the store's durability barrier; none of the three is admin-gated. Memory is project-scoped (pass `project`). Memory reads and item writes accept `X-Hoody-Realm` or `?realm=` to select `global` or a realm id (in the SDK, pass `agentRealm` in the method's options); omitted, the agent's current realm is used. A realm this login does not serve returns `404 not_found`; an agent pinned to one realm refuses another with `400 realm_scope_unsupported`. If the selected realm's memory is not connected, the request returns `503 service_unavailable` with `Retry-After` and does not connect it. `hoody agent memory consolidate` is a guarded write: it needs a single-use intent from `hoody agent memory writeintents create`; see Common errors. `hoody agent memory search` / `hoody agent memory graph get` also return `503 store_unavailable` while the store is still warming — retry rather than treating it as an empty result.
- **Todos** — `hoody agent todos list` / `hoody agent todos create` to file; then `hoody agent todos triage` (LLM inbox pass), `hoody agent todos claim` / `hoody agent todos release`, `hoody agent todos start` (dispatch a background orchestrator — returns `{job_id, session_id}`), `hoody agent todos cancel` to abort an in-flight run, and `hoody agent todos proposals approve` / `hoody agent todos proposals deny` to resolve a proposed run — approve is NOT inert: it spawns a background worker session equivalent to `hoody agent todos start` (a J-class autonomous run that spends model budget), while `hoody agent todos proposals deny` spawns nothing — plus `hoody agent todos snooze` / `hoody agent todos archive`. To move a todo between states (`inbox`, `ready`, `blocked`, `review`, `done`, `dropped`) or edit its fields, `hoody agent todos update` applies a CAS-guarded patch / `state` transition (`in_progress` is entered only by `hoody agent todos claim` / `hoody agent todos start`; `hoody agent todos update` refuses it, and an unknown state is rejected) — read the todo's OWN `revision` with `hoody agent todos get` and pass it back (`hoody agent todos revision get` is a change cursor filtered by realm and account visibility, NOT the per-todo CAS token; a stale value → `409 todo_conflict`); a stale revision is rejected (409). `hoody agent todos archive` is not terminal — `hoody agent todos archived purge` permanently and irreversibly deletes archived todos of the selected realm that were archived more than 90 days ago (and those with a missing or invalid archive time); a read-only todo from before the computer rename is kept; no confirmation gate, treat as destructive. Mind the comment split: `hoody agent todos comments create` (`/messages`, plural) only appends a comment, whereas `hoody agent todos messages send` (`/message`, singular) ALSO kicks an orchestrator turn — a budget-spending LLM run that returns `{job_id}` — so use the plural form for a plain note. The `job_id` returned by `hoody agent todos start`, `hoody agent todos messages send` and `hoody agent todos triage` completes as `succeeded` the moment the dispatch is accepted; it records the dispatch only, not the worker's outcome. Follow the todo itself (`hoody agent todos get`, its state and timeline) rather than polling that job. Note `hoody agent todos start` / `hoody agent todos triage` / `hoody agent todos proposals approve` are J-class autonomous runs with NO confirmation gate on the RPC (reaching the RPC is itself treated as the human approval; that denial lives only on the model-facing `run_todo` *tool*), so calling them from automation silently dispatches a real LLM run — gate them in your own caller.
- **Workflows** — `hoody agent workflows list` / `hoody agent workflows get` / `hoody agent workflows set` / `hoody agent workflows delete` / `hoody agent workflows hide` / `hoody agent workflows unhide` manage saved definitions; `hoody agent sessions workflows start` dispatches one onto a live session and returns a JOB, not a run (optionally seed the run with a `{ prompt }` body — input text fed to the workflow). `hoody agent workflows set` takes the whole definition as `definition`; a small definition that saves is `{"entry_point":{"id":"check"},"steps":{"check":{"type":"bash","command":"echo hello"}}}` (`steps` is a non-empty object keyed by step id; this example uses a `bash` step with a `command` and ends after that step because it has no `next_steps`). Save it as `workflow.json` and pass `--definition @workflow.json` — poll `hoody agent jobs get`, checking both `status` and `run_id`: once `run_id` populates (null during the brief dispatch window), track the run via `hoody agent workflows runs list` / `hoody agent workflows runs get` and stop it with `hoody agent workflows runs cancel`; a dispatch the agent refuses (a missing required input, a blocking hook, no configured model) ends the job as failed with `run_id` still null, so read its result and the session stream: no run exists to track or cancel; feed a running workflow with `hoody agent workflows messages send` (`{ text }`). Run events flow on the owning session's stream, not a per-run bus.
- **Bots** — `hoody agent bots create` opens a long-lived assistant that delegates work to sessions on computers; post to it with `hoody agent bots messages send` (HTTP 202; a busy Bot queues the message) rather than prompting its session, and see Examples for the full create, message, follow, forget, delete run. Replace its limits with `hoody agent bots guardrails set --id <id> --guardrails <guardrails>` (empty clears them): the Bot reads them before its next message and delegates opened afterwards receive them in their first prompt, while delegates already open keep theirs. `allowed_computers` and `allowed_agents` restrict the delegates it opens next (empty means any) and `yolo: true` (default false) asks delegates to approve tool calls automatically. Check `yolo_unapplied` in `hoody agent bots get`: `pending` means a delegate has not confirmed the change yet and it is sent again; `refused` means that delegate's approval policy does not allow YOLO, so it keeps asking for approvals and the change is not sent again until `yolo` changes. `hoody agent bots logs stream` and `hoody agent bots logs get` carry finished rows only; for live reply text, thinking and tool calls follow the Bot's `session_id` (from `hoody agent bots get`, it changes after `hoody agent bots reset`) with `hoody agent sessions stream`, and do not answer questions on that session whose `frame_request.kind` starts with `bot.`, because the Bot runtime answers them. To stop only the Bot's running turn, cancel its `session_id` with `hoody agent sessions turns cancel --id <session_id> --turn-id <turn_id>` (there is no `bots` command for it), naming the `turn_id` that `hoody agent bots get` shows while `turn_running` is true.
- **Share a Bot through a public URL** — a Bot URL, `https://<label>.hoody.bot`, lets a person with no Hoody account talk to one of your Bots with a named key (`hbk_…`) you hand out. It belongs to your account, not to the agent kit: `hoody boturls create` and `hoody boturls keys create` manage it, and `hoody boturls ask <url> "…"` is the caller side. You name the Bot by the `realm`, `id` and `uid` that `hoody agent bots get` returns. A Bot has one Bot URL at most, a deleted and recreated Bot has a new `uid` that the URL does not follow (`repoint` it), and everyone holding a key shares one conversation with the Bot. Example 4 runs the whole flow (create, key, call, rotate, panic); the `## Bot URLs` section of the appendix is the reference for the doors, the caller client and the errors.
- **Audio / voice** — the kit speaks and listens through the speech models it lists. `hoody agent audio models list --capability tts` or `hoody agent audio models list --capability stt` lists the text-to-speech and speech-to-text models with their formats, rates, languages and whether their provider has a key; `hoody agent audio voices list --model <spec>` lists a model's voices (omit `--model` for the voices of every available model except the Hoody AI relay ones, which are listed only when named with `--model`). `hoody agent audio speech create --input "<text>" --response-format mp3 --out-file hello.mp3` speaks the text (at most 4096 characters) and writes the audio as one file; the streamed form of that call (SSE frames of base64 audio) has no CLI command, since a terminal can neither play nor show them. Transcription takes a `multipart/form-data` upload, which has no CLI command: post the recording over HTTP to the kit URL (`hoody open agent --url` prints it) with `curl -sS -X POST "${K%/}/api/v1/agent/audio/transcriptions" -F file=@recording.wav` (`-F language=…`, `-F model=…`, `-F prompt=…`, `-F response_format=…` optional; wav or mp3, at most 16 MiB and 600 seconds) to get `{ text }` with the default `response_format` `json` (`text`: the plain transcript; `verbose_json`: `text` plus `language`, `duration` and `segments` when the model gives them), or `…/transcriptions/stream` for the SSE form (`transcript.text.delta`, then `transcript.text.done` with the whole `text`), wav and mp3 only, for models with partial results. A capability the model lacks (a format, `instructions`, a `speed`) is refused `400` before any paid call; `response_format` is `mp3`, `wav` or `pcm` (16-bit little-endian mono, no header; omitted: `wav`, or `mp3` when the model gives no wav, and on a stream `pcm`, else `mp3`). Some transcription models also take webm, ogg, m4a or flac on the non-streaming call (the model's `opaque_formats`): Hoody passes those on undecoded, does not verify their duration, and bills the provider's reported duration or the model's maximum when none is reported. Every speech call is billed, a stream included, so do not replay a stream automatically; a failure before the first frame is an ordinary JSON error with its status, after it an `error` frame, and a `: ping` comment arrives every 25 s. `X-Hoody-Realm` (or `?realm=`, `--agent-realm`) names the realm the call is billed to; omitted, the agent's current realm. The cwd, config-dir and computer headers are refused `400 realm_scope_unsupported`.
- **Spoken messages to a Bot** — `POST /api/v1/agent/bots/{id}/messages/audio` over HTTP (`curl -F file=@recording.wav -F language=en`; a multipart upload has no CLI command, so use HTTP or the SDK) transcribes one recording (wav or mp3, at most 16 MiB and 600 seconds) and queues the transcript as a message to the Bot exactly like `hoody agent bots messages send`: `202 { message_id, state: 'posted' | 'queued' | 'dropped', turn_id?, transcript }`. `dropped` means the Bot dropped the message before posting it and never will post it (`reason` says why); that key keeps answering `dropped`, so send the recording again under a new key. Audio with no speech in it is answered `200 { no_speech: true }` and nothing is queued or billed. Send an `Idempotency-Key` on anything you may retry: once the message is admitted, the same key with the same audio, the same `language` and the Bot's same `speech.stt_model` and `speech.stt_prompt` returns the same `message_id` without transcribing again (a replay of a finished one has no `transcript`; a retry that waited on one still running gets it), and the same key with any of those changed is `422`, even for the same recording. A transcription that failed or was refused stores nothing, so a retry with that key transcribes again; a recording with no speech in it is answered `no_speech` each time, without a transcription. At most 4 recordings per Bot are transcribed at once (`503 speech_busy` past it); a request repeating the key of one still running waits for it (`429 speech_busy` when too many wait); `409 bot_deleted` or `bot_reset` means the Bot was deleted or reset before the recording was admitted. The Bot's `speech` settings (`tts_model`, `stt_model`, `voice`, `language`, `speed`, `speak_wakes`, `speak_gates`) choose the models and voice used for its spoken messages and replies.
- **Talk to a Bot by voice (WebSocket)** — `GET /api/v1/agent/bots/{id}/voice` upgrades to a WebSocket (request it with `Sec-WebSocket-Protocol: hoody.voice.v1`) that carries the user's speech to the Bot and the Bot's spoken replies back (from a terminal, `hoody agent bots voice connect --id <bot>` records the microphone and plays the reply through the audio programs already installed, push-to-talk by default, `--mode vad` for hands-free; `--in-file question.wav --once` sends one 16-bit PCM mono WAV at 8000, 16000, 24000 or 48000 Hz and exits 0 when the answer arrived, its turn did not fail and its speech did not fail, else 1 with the reason (2 when the flags conflict or no computer is selected); `--audio-output none` asks for text-only replies; `--doctor` prints the readiness check below with the local audio checks, and the check has no command of its own). The readiness check behind `--doctor` answers 200 either way with `{ ready, speak, stt, tts, max_utterance_secs, diag_id? }`: `stt` and `tts` (`null` with `speak=false`) each carry `ok` and `model` (plus `language` or `voice`), and when `ok` is false also `code`, `reason`, `message`, `retryable` and, when known, `retry_after_secs` and `diag_id`. It follows the inference path (the Bot's own model, else the agent's `audio.stt_model` and `audio.tts_model` settings, else the Hoody AI voice relay when the audio setting `relay_default` is on; then capability, voice and language, then key), runs no inference, bills nothing and takes at most 6 s; `ready` is not a promise that the provider will answer. `require=stt`, `require=tts` or `require=stt,tts` on the voice URL runs the same check before the upgrade and refuses it `400 bad_request` when every failure is a voice or language the model does not offer, else `503 speech_unavailable`, with the check's result in `details` (messages may be shortened and the echoed model, voice and language values removed to fit the error's size limit; `details` is omitted if the reduced result still does not fit); a refused check takes nothing over; omitted, nothing is checked; `require=tts` with `speak=false` is `400`. `speak=false` gives text-only replies: no speech is made, every `reply.final` has `spoken: false`, nothing is billed for synthesis (speech-to-text still is), and the `session` frame shows `speak: false`. An agent supports `require`, `speak` and the check when `GET /api/v1/agent/version` lists the capability `bot_voice_check` with `supported` and `available` true. `mode` is fixed for the connection (default `vad`); in `ptt` mode only audio between `ptt.down` and `ptt.up` counts and other audio is dropped. One utterance is at most 60 seconds, or the speech-to-text model's limit when lower. Binary frames from the client are input audio: one byte `0x00`, a big-endian unsigned 32-bit sequence number, then 20 to 200 ms of audio in `in_format` (`pcm16` default, `pcmu`, `pcma`) at `in_rate` (8000, 16000 default, 24000 or 48000); binary frames from the agent are output audio: one byte `0x01`, a big-endian unsigned 32-bit output number, a big-endian unsigned 32-bit sample offset, then 16-bit little-endian PCM at `out_rate` (default 24000). Text frames are JSON objects with a `type`: the client sends `input.commit`, `ptt.down` / `ptt.up` (`mode=ptt`; the default `vad` lets the agent hear when the user starts and stops), `output.cancel`, `playback.mark` (with `play_lead=true`, at least every 500 ms while playing), `own_gate.decide` / `own_gate.answer`, `text` and `ping`; the agent sends `session` first, then `vad.start` / `vad.end`, `transcript.partial` / `transcript.final`, `reply.provisional` / `reply.invalidate` / `reply.final` / `reply.diverged`, `output.start` / `output.end` / `output.stop`, `cancel.result`, `gate.announced`, `own_gate.pending` / `own_gate.resolved`, `busy`, `error`, `takeover` and `pong`. A spoken message counts once the Bot's log shows it; only replies to this connection's own messages are spoken (plus the Bot's own replies with `speak_wakes`), and every reply's final text still arrives in `reply.final` (at most 64 KiB: a longer text is cut and `truncated` is true; the whole text is in the Bot's log). Voice never answers a delegate's approval or question: answer it on screen or by typing. One connection controls a Bot's voice at a time, over this route, the Realtime route or a phone call: a second is refused `409 voice_busy` unless it asks `takeover=true`, which closes the first (it receives `takeover`, close 1000). `reply.final` carries `own: true` when its turn answers a message sent on this connection, `false` when it does not, and no `own` when the connection cannot tell; `own` is about this connection only: a new connection starts at the next event, so a reconnect that misses the turn start gets no `own` on that reply (not `own: false`), and when it is absent match the reply's `turn_id` and your `message_id` in the Bot's log. A speech failure carries `error { code, reason?, message, diag_id?, retryable, retry_after_secs? }`: on `transcript.final` when it `failed` or was `rejected` `stt_suspect` (the outer `failed` value is unchanged; branch on `error.code` when present), on `reply.final` when `reason` is `tts_failed` or `tts_incomplete`, and on an `error` frame with code `service_unavailable` when the speech service failed while a gate announcement was spoken (at most once per code and reason per connection; the connection stays open; an announcement stopped for the daily speech limit, or silenced because speech output is off, sends no error frame). `message` says what happened and what to do next; `diag_id` names the failure in the agent's log. A `pcm16` frame of an odd byte length, a sequence gap, or audio faster than 1.5 times real time over 2 s counts as lost: the open utterance ends `rejected: frame_loss` and the connection stays open. The connection closes 1000 when the client closes it, after 10 minutes without a frame from the client (the Bot's output does not count; send `ping`), on takeover or when the Bot is deleted or suspended; 1001 when the Bot is stopped (as when the agent shuts down); 1002 without the subprotocol; 1008 for a malformed frame, text frames faster than 50 a second once the burst of 100 (the bucket starts full) is used up, an input frame outside 20 to 200 ms or a `playback.mark` past the audio sent; 1009 for a frame over 64 KiB; 1011 when a write fails, the agent runs out of voice memory, or on an internal error (a client that does not read gets no close frame; the connection just ends). The Bot's own approvals and questions (`own_gate.decide` / `own_gate.answer`) report their outcome in `own_gate.resolved` (`applied`, `resolved`, `stale`, `unavailable`, `not_offered`, `no_pending_gate`, `stale_gate`, `gate_cancelled` or `decision_unconfirmed`), never as an HTTP status.
- **Talk to a Bot with an OpenAI Realtime client (WebSocket)** — `GET /api/v1/agent/bots/{id}/realtime` upgrades to a WebSocket that speaks the OpenAI Realtime protocol (GA event names), so an off-the-shelf Realtime client library talks to the Bot (SDK and HTTP only; no CLI command). The client sends `session.update`, `input_audio_buffer.append` / `.commit` / `.clear`, `conversation.item.create` / `.delete` / `.retrieve` / `.truncate`, `response.create` and `response.cancel`; the agent answers with the matching server events (`session.created` first). Input audio is `audio/pcm` (24000 Hz, 16-bit little-endian, the default), `audio/pcmu` or `audio/pcma` (8000 Hz); output audio follows the session's output format. With `server_vad` the agent hears when the user starts and stops speaking and answers on its own; without turn detection the client commits and asks with `response.create`. A user item reaches the Bot once, by its id, and the Bot never forgets an id it has seen, so a client replaying its history on reconnect does not resend an old item; at the Bot's limit (`realtime_items` on the Bot) a new item is refused and the connection closed. An event that would change an item already sent (deleting, truncating or editing a user item waiting for a response) closes the connection with 1008; so do a binary or non-JSON frame, a frame over 1 MiB, control events faster than 50 a second once the burst of 100 (the bucket starts full) is used up, and input audio faster than 1.5 times real time. The same one-controller rule applies: `409 voice_busy` unless `takeover=true`. A WebSocket upgrade of the Bot's own OpenAI base URL plus `/realtime` (`…/api/v1/agent/bots/<realm>/<bot>/v1/realtime`, the `urls.openai` of `hoody agent bots get` plus `/realtime`) opens the same connection for a Realtime client that only takes a base URL, with the same `?takeover=true`.
- **A phone call as the Bot's voice** — `GET /api/v1/agent/bots/{id}/twilio` is the WebSocket URL for Twilio's `<Connect><Stream>` instruction: one Twilio Media Stream becomes the Bot's voice controller (no CLI command: the peer is a phone call's media stream, not a terminal; follow the call's effect with `hoody agent bots logs stream --id <bot>`). Audio is μ-law at 8000 Hz, mono; Twilio's `connected`, `start`, `media`, `mark`, `stop` and `dtmf` events are taken as Twilio documents them. What the caller says is cut into utterances by voice activity detection, each transcribed in order and posted to the Bot as the user's message; the reply comes back as 20 ms media frames with one `mark` per spoken segment, and a caller speaking over the reply stops its playback (a `clear` is sent). A `stop` event, or the call ending, drops the utterance still being spoken (never transcribed or posted); complete ones are still posted. DTMF digits are ignored, and gates are never announced or answered by voice. A second controller is refused and its stream closed with code `1008` unless the `start` event's custom parameter `takeover=true` (or `?takeover=true` on the URL) asks to take over from the open one. Access to this URL is controlled by the agent's proxy permission rules; configure one before pointing a Twilio number at it. Live Twilio accounts are not supported in this release: the route is tested against a Twilio Media Streams simulator.
- **Agent profiles** — `hoody agent definitions list` to enumerate named profiles; `hoody agent definitions create` / `hoody agent definitions copy` / `hoody agent definitions rename` / `hoody agent definitions delete`; `hoody agent definitions source get` → edit → `hoody agent definitions source set` (pass the `revision` from `hoody agent definitions source get` as `hoody agent definitions source set --expected-revision <rev>`: a stale one is refused `409 revision_conflict` and nothing is written; without it the save is unconditional); `hoody agent definitions model set` / `hoody agent definitions tools set` / `hoody agent definitions tools toggle` / `hoody agent definitions turnlimit set` / `hoody agent definitions reset`. The product-owned `bot` profile (the one a Bot runs) allows only a model pin through `hoody agent definitions model set` (an empty model clears it); `hoody agent definitions source set`, `hoody agent definitions tools set`, `hoody agent definitions tools toggle` and `hoody agent definitions turnlimit set` are refused for it with `400 bad_request`, as are creating over it and renaming it, and a Bot's own `model` overrides the pin. To make a session use a profile, `hoody agent sessions agent set` (`{ agent }`; not `bot`, `script-writer` or `github-installer`, see step 4) — that selects, it does NOT edit the profile. Two daemon guard rails: `hoody agent definitions delete` refuses the configured default chat agent, and a shipped-default profile that has no removable override of its own (`is_error:true` — use `hoody agent definitions reset` or `hoody agent definitions source set` instead); in a realm that holds its own saved override of a shipped profile, deleting it removes the override and the shipped version shows through again, and `hoody agent definitions reset` refuses a profile that has no shipped default (`is_error:true`).

### 6. Fire-and-observe, recurring prompts, and re-attach

- **Fire-and-observe** — `hoody agent sessions turns start` with `{ text }` dispatches a turn and returns `{ job_id, session_id, turn_id }` immediately (HTTP 202) without streaming or blocking; watch completion via the `agent_done` on the session event stream (a connected `hoody agent sessions stream` socket, or `hoody agent sessions stream`) whose `turn_id` matches (another client's turn on the same session ends with its own `agent_done`). A cancel scoped with that `turn_id` stops only this turn. Refuses with 409 `turn_in_flight` if a turn is running, or 409 `gate_parked` if a gate is open.
- **Observe / re-attach** — `hoody agent sessions stream --id <sessionId>` follows a live session's full `event.*` stream over SSE; the CLI has no WebSocket form, so a WebSocket attach is SDK or HTTP only. Either way, pass `since` (gateway int64 seq, or the `Last-Event-ID` header) to resume from the 1024-event replay ring after a disconnect (a gap past eviction yields `event: lagged {code:replay_gap}`). Each frame is `{seq, incarnation, event}`, and a session re-attached under the same id starts a new incarnation whose `seq` restarts at 1, so send `incarnation` (the one you last saw) together with `since`: a mismatch answers `replay_gap` plus the full retained ring instead of silently resuming into a different history. Over SSE the `event:` line drops the `event.` prefix (`event.agent_done` arrives as `event: agent_done`) while the JSON `data:` keeps the full name, so match ordinary event frames on the parsed payload's `event.type` (for example `event.agent_done`); control frames (`lagged`, `end`, `replay_boundary`) have no `event` key. `hoody agent sessions replay` returns the buffered event tail of a *live* session (with `min_seq`/`max_seq`) for a one-shot catch-up (only a *live* session has this ring). `hoody agent sessions stream` does not revive a session either: on a persisted but non-live session it answers `404 not_found`, so re-attach it first (`hoody agent sessions create --attach-session-id <id>`), then open the stream.
- **Recurring prompts (loops)** — `hoody agent loops create --session-id <sessionId> --prompt <prompt> --interval <interval>` (plus optional `max_runs` / `stop_when` / `max_cost_usd` / `max_wall_ms` caps) schedules a prompt to re-fire on a live session; `hoody agent sessions loops list` / `hoody agent loops update` (pause via `{ paused: true }`) / `hoody agent loops delete` to manage, `hoody agent loops runs start` to fire one immediately. Loops are entirely session-scoped. Three rules refuse a request rather than adjusting it: `interval` has a floor of 60 seconds; at most 8 loops can be active (not paused, not ended) per daemon, so the 9th create is rejected; and each `hoody agent loops update` carries at most ONE intent (`paused`, or `expires_in`, or the budget fields `max_cost_usd` / `max_wall_ms`), so a request mixing two is rejected 400 (a body with none of them is treated as a budget update).

- **Stop the realm's work** — `hoody agent work stop` (with the required `--all`) acts on at most 256 items per call: when the answer has `complete: false`, send its `next_cursor` back as `--after`; a `complete: false` answer with no `next_cursor` (work started during the call, or items behind the cursor) is answered by calling again without `--after`. Synchronous and streaming tool and headless requests end when their HTTP request closes and are not covered.

### 7. Headless one-shot run

The run's shape is chosen by the request BODY, not by a header: the default (`format` `text` or `json`) is an async job — HTTP 202 `{ job_id }`, then poll `hoody agent jobs get` and fetch the output with `hoody agent jobs result get` — while `format: "stream-json"` (or `stream: true`) streams the run over SSE (`start` → `result` or `error` → `end`). A failure after the acknowledgement (a timeout, `admin_unauthorized`) arrives later, in the job result or as the `error` frame, never as the HTTP status. A headless run approves every plan and every ordinary confirm, denies a `human_only` confirm and one carrying a `helper_id` (the tool call then fails), and answers every question itself (the first rich-option title, else the first plain option, else an empty answer), so treat it as arbitrary code execution. `hoody agent headless start --prompt "<task>"` prints the 202 `{ job_id }` (`--format` is `text` or `json`); poll `hoody agent jobs get --id <job_id>` and fetch the output with `hoody agent jobs result get --id <job_id>`. Use `hoody agent headless start --prompt "<task>" --stream` to print the SSE frames as they arrive instead. For a one-shot turn that needs no job, `hoody agent prompt "<task>" --wait` creates a session and blocks until the turn completes (add `--gate-policy auto_approve` to auto-approve confirm gates; questions still park the turn).

### 8. Configure MCP servers for a session

Reads first: `hoody agent mcp list` (`{ session_id }`) returns the EFFECTIVE merged `mcp_servers` config, the per-layer settings files behind it, and each server's LIVE runtime state (connected, negotiated protocol revision, tool count, pid, revocation reason, recent stderr). Every write is TWO steps: `hoody agent mcp writeintents create` (`{ session_id, op, scope }`, op ∈ the strings "upsert", "delete", "set_enabled" and "import", scope ∈ `user`|`project`|`local`; an omitted scope means `user`, or `project` when the session has no user layer, which is the usual case for a computer session — read the returned target path to confirm where the write lands) mints a single-use nonce bound to {session, op, resolved settings path} and returns the target path plus the current `mcp_servers` hash — then present that `nonce` plus the hash as `expect_hash` on the matching `hoody agent mcp upsert` / `hoody agent mcp delete` / `hoody agent mcp enable` / `hoody agent mcp disable` / `hoody agent mcp import`. BOTH are required on every write: skipping step one fails closed, a nonce minted for a different op or scope fails closed, and `expect_hash` has no omit-it default — a first write into a settings file that does not exist yet states that expectation with the empty-array hash rather than leaving the field out. To adopt someone else's config, preview it with `hoody agent mcp import --preview` (`{ session_id, document }` — writes nothing, needs no nonce, strips credential values) and then `hoody agent mcp import` with a fresh `op: "import"` nonce; imported servers land DISABLED, so enable each one with `hoody agent mcp enable`. After editing a settings file by hand, or to recover a server that died, `hoody agent mcp reconnect` (`{ session_id }`) re-reads the layers and reconciles every live session's pool — a healthy unchanged server is not restarted. `hoody agent mcp test` trials a candidate config without saving it, but it is human-only (see Common errors).

## Quirks & gotchas

- **Settings take a JSON patch, and its JSON types matter.** `hoody agent settings update --patch '{"model":null}'` (or `--patch @patch.json`, or `--patch @-` to read it from standard input) merges the top-level keys of `patch` into the home `settings.json`, one level deep: a key set to `null` is deleted, while the string `"null"` is stored as text, and a nested object replaces the whole stored value of its key (a dotted key such as `"a.b"` is one top-level key, not a path). Guardrail keys cannot be changed this way and answer `403 settings_key_protected`: `deny_list`, `deny_urls`, `features`, `allowed_directories`, `hooks`, `disableAllHooks`, `mcp_servers`, `tools`, `rules`, `rules_timeout_ms`, `shipped_hooks`, `exec_trust` and `audio` (so `audio.tts_model` / `audio.stt_model` are set in settings.json on the computer, not over this API). A non-null top-level `model` is refused 400: pin a model with `hoody agent definitions model set` or `hoody agent sessions model set`, while `{"model":null}` still deletes an old value.
- **A chat nobody has named gets its title from the agent.** After the chat's first finished exchange, a model writes a short title into the session's `name`; `event.session_renamed` carries the new name. A name set with `hoody agent sessions rename --id <id> --name "<title>"` is never replaced, and an empty name asks for a new title (at once on a live chat, after its next finished turn on a closed one). Turn titles off with the `session_titles` feature (`hoody agent settings features update --features session_titles=false`). The home settings key `session_title_model` (a `provider/model`) picks the model; absent, each chat uses its own (a Claude Code session uses Hoody's helper model, and a fusion chat gets no title). Daemon-managed sessions and a Bot's own sessions are not titled.
- **`--definition` (`workflows set`), `--patch` (`settings update`), `--params` and `--payload` take one JSON document from any of three sources.** Inline (`--definition '{"entry_point":…}'`), from a file (`--definition @workflow.json`) or from standard input (`--definition @-`); each form sends the same JSON. Only one flag of a command can read standard input. `fusions set` takes no document for the composite as a whole: it is typed flags (`--spec-name`, `--spec-method`, one `--spec-members spec=<model>,role=<role>` per member, and settings such as `--spec-params-rounds`); only `--spec-members` also accepts the whole member list as one JSON array. `models get --spec` takes a plain model spec such as `acme/llama-3.3-70b`.
- Bare `hoody agent` (no subcommand) is `hoody hub`: it opens the Hub, on the page the last run ended on (else Home); a computer given (an id or a name, as the argument or with `-c`) is checked first, but the Hub does not open on it. It is separate from this HTTP namespace, the typed control surface. The CLI does not attach the agent's own TUI: it opens at the computer's `agent-1` URL, or in a terminal session started with `agent=true`.
- On the realm-scoped agent commands (Bots, sessions, gates, loops, todos, workflow runs, changes and stop calls), an explicit `--realm global` or `--realm <24-hex-id>` also scopes the agent request, through `X-Hoody-Realm`; `--realm all` lists every served realm on the Bots, sessions, gates, loops, todos and workflow-runs list commands. A `--realm` that disagrees with the command's own `--agent-realm` is refused before anything is sent, and a saved or environment realm default is not forwarded this way, except by the hand-written `hoody agent bots voice connect` (its `--doctor` check included), which sends the realm it resolves, a saved or environment default included. Everywhere else the global `--realm` only picks the platform API host that resolves `-c` to the computer (`--realm global` is the base host), and a route that serves only the active realm refuses a per-request realm with 400 `realm_scope_unsupported`.
- Source of truth is the agent kit's own OpenAPI document. Its `GET /api/v1/agent/openapi.{json,yaml}` routes are not reachable through the kit URL (the proxy refuses them), so use the agent reference bundled with this skill for request paths and schemas; every route lives under the single `/api/v1/agent` prefix. The kit checks no credential of its own and asks for no bearer header; access is decided by the computer's proxy permission policy. 403 `forbidden` — Refused by the Source IP Guard: Hoody Kit programs are reached through their URLs only.
- The proxy service slug is `agent` and the kit URL host carries the index segment (`-agent-{index}`). The CLI resolves it from `--computer` / `-c`; you do not build it by hand.
- `hoody agent sessions turns run` waits for the turn to end (or returns `{pending_gate}` the moment a turn parks on a confirm/question), but at most until the server deadline (290 seconds by default): a turn still running then answers `503 service_unavailable` with `details.turn_running: true` and keeps running; prefer streamed prompting for anything non-trivial so you can observe progress and resolve gates as they arrive. (Stream the turn with `hoody agent prompt "<task>" --session-id <id>` (`-c` picks the computer, not the session); it reads the daemon's SSE for you. `hoody agent sessions turns start --id <id> --text "<task>"` is the raw fire-and-observe form: it dispatches the turn and prints the 202 `{job_id, session_id, turn_id}`. Add `--stream` to follow the session event stream instead; that stream does not end with the turn, so stop at the `agent_done` carrying your `turn_id`. `hoody agent sessions turns run` is the blocking form.) For non-interactive turns where you cannot resolve gates by hand, enable the `auto_approve` gate policy to answer the lead's confirm gates (off by default; a gate raised by a helper agent waits for a person). On the blocking form (`hoody agent sessions turns run`, route `prompt:sync`) it stays on for the dispatched turn even after the request ends (for at most 24 hours), unless its watcher falls behind and is dropped, after which later gates of that turn need a person. On the streamed form (route `prompt:stream`) it is tied to the connection, not the turn: disconnecting before the turn ends stops it, and while the stream stays open it also answers confirm gates of LATER turns on the same session, so close the stream at your turn's `agent_done`. With either form, an ordinary confirm gate is approved, a gate raised by a tool-call rule and a destructive-shape gate (cause `static_stakes`: a recursive force delete, curl piped to a shell, `sudo`, a force push) are DENIED, a `human_only` confirm gate is never answered: it waits for a person (on `prompt:sync` it comes back as `{pending_gate}` with `human_only: true`), and a session whose approval policy is `always` refuses the policy with `409 approval_policy_active` before the turn starts. CLI: `hoody agent prompt "<task>" --gate-policy auto_approve`, or `hoody agent sessions turns run --id <id> --text "<task>" --gate-policy auto_approve` for the blocking form; bare `hoody agent` has no such flag. This only answers **confirm** gates, never questions.
- **The agent's shell has the computer user's own sudo.** The agent runs as the computer's `user`, and its bash tool can use sudo exactly as that user can without a password: with the default passwordless sudo it can `sudo apt-get install`, `sudo systemctl enable --now` a unit and so on. When `user` has no passwordless sudo (the drop-in removed, a password required), the agent's shell has none either, because there is no terminal to type a password into; a policy that allows only some commands without a password allows the same commands to the agent (with sudo's default `listpw`). While the agent's shell can sudo, a session's `dir_scope` (`home`) no longer confines its bash commands: the file tools still keep to the scope, but the shell can reach the whole computer, like the terminal kit. To take sudo away from the agent, take passwordless sudo away from `user` (`SKILL-CLI.md` § Default user); the agent keeps everything else `user` has, such as Docker through the `docker` group.
- Every prompt/gate/cancel call is **session-scoped** — you must hold a session id from `hoody agent sessions create` first; there is no implicit default session. Hook writes are session-scoped too (the guarded writes — `hoody agent hooks upsert` / `hoody agent hooks delete` / `hoody agent hooks enable` / `hoody agent hooks disable` / `hoody agent hooks enable --all` / `hoody agent hooks disable --all` — plus `hoody agent hooks writeintents create`, and the side-effecting `hoody agent hooks run` / `hoody agent hooks trust`, all require a live `session_id` — `hoody agent hooks trust` clears the per-session hook-trust prompt (the execution-trust probe `hoody agent hooks list` reports), the gate that must be acknowledged before a saved hook command is allowed to fire, mirroring `hoody agent skills trust` for skills; `hoody agent hooks reload` with a `session_id` reloads only that session and returns its summary, and without one reloads every live session in the realms the caller is served) AND the config writes are nonce-guarded (`hoody agent hooks run`, `hoody agent hooks trust` and `hoody agent hooks writeintents create` itself need a live `session_id` but no nonce, and each call still needs its own fields): call `hoody agent hooks writeintents create` (`{ session_id, op, scope }`, op ∈ upsert|delete|toggle|set_disabled|rules_set; `rules_set` is for `hoody agent hooks rules set` and needs its own matching nonce) to mint a single-use nonce, then pass that `nonce` on the matching `hoody agent hooks upsert` / `hoody agent hooks delete` / `hoody agent hooks enable` / `hoody agent hooks disable` / `hoody agent hooks enable --all` / `hoody agent hooks disable --all` — the nonce binds to that session+op+scope tuple and the write fails closed without it. Note hooks are an arbitrary-command surface: `hoody agent hooks upsert` persists a command that fires on lifecycle events, and `hoody agent hooks run` on a command hook runs a command at once: running saved hooks goes through the session's hook-trust gate, while a run that supplies an unsaved inline `command` runs it without that saved-hook trust check. Every command-hook run is refused (`approval_policy_unsatisfiable`) while the session's approval policy is `always`, and `hoody agent hooks test` of a shipped hook only evaluates its trigger without running anything. These calls carry no confirmation step of their own — the same access that authorizes any agent-kit call authorizes these too, with nothing extra — so add your own confirmation before exposing this surface to an autonomous caller.
- **`env` and `headers` VALUES are never returned by the MCP surface; every other field comes back verbatim.** `hoody agent mcp list` reports `env_keys` / `header_keys` — key NAMES only — because a redacted value invites a client to write the placeholder back as the real secret; a write whose body carries the redaction placeholder for a credential is REFUSED rather than stored. Other fields, including `url`, `command` and `args`, are echoed verbatim in a listing (only the import preview differs: it shows each entry as it would be stored, with a missing `type` becoming `http` when `url` is set, `${env:VAR}` references translated in `env` and `headers` only (others stay as written, with a warning), an env-file setting dropped with a warning and `enabled` false, and `env` and `headers` replaced by `env_keys` and `header_keys` name lists), so a credential embedded in one of them (a token in a URL, a key on a command line) is NOT redacted: keep secrets in `env` / `headers`, and treat the rest of a listing as sensitive. To change a secret you must supply its real value; to leave one alone, omit the field — `hoody agent mcp upsert` merges FIELD BY FIELD over the existing entry of the same name, so omitted fields keep their stored value (including fields this build does not model), and `env` / `headers` merge per key (a key set to `null` is deleted, `{}` clears the map). A genuine re-point (a changed `type`, `command`, `args` or `url`) clears `env` and `headers` unless the same request re-supplies them, so send the credentials the new target needs in that write; restating the identity you read back is not a re-point. `hoody agent mcp enable` / `hoody agent mcp disable` flip only the `enabled` flag so credentials and options survive a disable. A deleted, disabled, or re-pointed server is REVOKED in every live session before the response returns, including mid-turn (a stdio child is reaped when its last holder releases). Reconnecting is awaited only for the session named in the request: check `servers[].connected`, because a failed connection still answers 200. Other live sessions reconnect in the background, best effort, and a session mid-turn adopts added tools at its next turn boundary. Import is WHOLE-BATCH — one bad entry aborts everything — it understands the hoody (`mcp_servers` list), Claude/Cursor (`mcpServers` map) and VS Code (`servers` map) dialects, and REFUSES a document carrying more than one of them rather than guessing.
- `POST /api/v1/agent/hoody/auth/bootstrap` (HTTP only; no CLI command) (token bootstrap) is enabled by default; a deployment can turn it off, and then every call answers 404. Browser clients may call it; the `Content-Type` media type must be `application/json` (parameters such as `charset=utf-8` are accepted). Where the deployment requires a capability, the body must carry the matching `capability` (a mismatch is also 404). The token must belong to this box's owner and carry the full login grant (otherwise 403). On a box with no credential it installs (201 `installed`) and adopts any local sessions or todos that have no owner; on a box logged in to the SAME account it replaces the stored token whether or not it expired (200 `renewed`). A token for a different account is refused `409 agent_login_conflict`, and a credential supplied through the environment is never replaced (`409 credential_present`).
- A Bot URL is bound to a Bot by its `uid`, not its id: if the Bot is deleted and created again, the Bot URL refuses keyed calls with `bot_disabled` (403) until the owner points it at the new Bot with `repoint`. The agent serves a Bot URL's doors but does not create, list or manage Bot URLs; they are an `api` resource that only the project owner (or an administrator) can manage.
- **A keyed request whose answer was lost is recovered by its key, never by sending it again under a new one.** Read the key first: `hoody agent sessions createkeys get`, `hoody agent sessions turns keys get`, `hoody agent sessions commands keys get`, `hoody agent bots messages keys get`. A hit is what the key admitted. A miss proves nothing: the request may still be on its way. For a create, turn or command, retire the key (`retire` in the same command group): `admitted: "false"` means nothing ran and nothing ever will (the late request is refused `409 create_key_retired`, `turn_key_retired` or `command_key_retired`), so a new key is safe; `"true"` returns what the key admitted; `"unknown"`, or a `503`, means it may have run: check before sending again. A create sent with a config dir keeps its key in that install: read and retire it with the same `X-Hoody-Config-Dir`. A Bot message has no retire: read the Bot's log.

## Common errors

- A model rate limit can end the turn: `event.error.code` is `quota_wait_too_long` or `rate_limit`, and `agent_done.error_code` carries the same code. For `quota_wait_too_long`, read `retry_after_secs` from the error payload, wait that many seconds, then send the message again: the turn ended instead of waiting. `retry_after_secs` is always present for `quota_wait_too_long` and may also appear on another failed model request when the provider named a wait (a rate limit or a busy provider); honor it when present, but do not assume it exists for `rate_limit`.
- A gate or question left unresolved stalls the turn — a streamed prompt that emitted an `event.confirm_request` (confirm gate) or `event.user_question` (question gate) will not complete until you answer it: `hoody agent gates approve` / `hoody agent gates deny` for a confirm, `hoody agent gates answer` for a question. For unattended runs, arm `hoody agent sessions autoreply update` (a self-driving auto-user loop; it answers questions only during its own rounds, so arming it does not resolve a question an ordinary prompt already parked), or pass the `auto_approve` gate policy on the prompt — but `auto_approve` only answers **confirm** gates (approving ordinary ones, denying rule-raised and destructive-shape (`static_stakes`) ones; refused with `409 approval_policy_active` on an `always` session), never questions or a `human_only` confirm gate; either still stalls: a question until `hoody agent gates answer` answers it (the auto-reply loop answers only the questions its own rounds raise), a `human_only` gate until a person answers it.
- `hoody agent sessions tasks list` and `hoody agent sessions tasks transcript get` return their data INLINE and need no live session and no attached stream. `hoody agent sessions tasks list` is the UNION of the live task registry and the session's PERSISTED task store (keyed by task id, live winning) — the live registry evicts completed tasks when a new one spawns, so a finished task can leave memory while its transcript is still durable, and a live-only list would hide it. `hoody agent sessions tasks transcript get` reads a task that reached a terminal state even for a closed session and after a daemon restart; a task still running when the daemon stops orderly is cancelled; if it does not stop within about 5 seconds shutdown tries to save its partial transcript as `cancelled` with `complete: false` (`source: "store"`); a saved row survives restarts, and one it could not save in time reads 404. A task running when the daemon is killed without that shutdown (crash, SIGKILL) leaves nothing and reads 404. Tasks never resume after a restart. Its `source` field is `"live"` or `"store"`, and `complete` reports whether the response reflects a terminal projection DURABLY COMMITTED to that store. `after_seq` is EXCLUSIVE (entries strictly after it, plus any still-open entry); OMITTING it returns the whole transcript, which is distinct from `after_seq=0`. `hoody agent sessions tasks cancel` / `hoody agent sessions tasks cancel --all` still act on a LIVE session and stop background tasks mid-turn (server-layer; tasks survive `hoody agent sessions turns cancel` but are not restartable).
- `hoody agent memory consolidate` (`POST /api/v1/agent/memory/consolidate`) is a **guarded write**: first `hoody agent memory writeintents create` with `{ op: "consolidate", project }`, then pass the returned `nonce` with the same `project` to `hoody agent memory consolidate`. The intent is single use, expires after a few minutes, and is bound to the store, the realm it was minted in, the op and the project, so a `wipe_project` intent or one for another project is refused. Without a valid intent the call returns `409 write_intent_invalid` and nothing is enqueued; every attempt that reaches the consolidate handler spends the intent, so such a retry needs a fresh one (a request refused earlier, such as a failed admin authorization or a 429, does not spend it). A `200` means the pass was enqueued and runs in the background, not that it finished. `503 consolidate_unavailable` means the maintenance queue is full or memory is disabled: retry shortly with a new intent. Consolidation spends model budget, so ask the user before running it.
- `hoody agent mcp test` (`POST /api/v1/agent/mcp/probe`) is **human-only and ALWAYS fails over this namespace** — probing STARTS A PROCESS (stdio) or makes an outbound request to a caller-chosen URL (http/sse), so a machine caller may not self-approve it: with a valid session it receives `403 human_only` on every HTTP/SDK/CLI call (a missing session id is refused `400` and an unknown or closed session `404` before that check). The surface still exposes it for completeness, it simply always refuses. The deny list is still enforced on the candidate config before anything is started. Use `hoody agent mcp import --preview` for a write-free preview instead; there is no programmatic substitute for the live trial.
- An MCP write needs BOTH a `nonce` and an `expect_hash` — neither is optional, and a stale hash is a CONFLICT rather than a silent overwrite. `hoody agent mcp upsert` / `hoody agent mcp delete` / `hoody agent mcp enable` / `hoody agent mcp disable` / `hoody agent mcp import` each require a fresh single-use `nonce` from `hoody agent mcp writeintents create` minted for that exact op and scope (one minted for a different op or scope fails closed) AND the `mcp_servers` hash you last read, from either `hoody agent mcp writeintents create` or `hoody agent mcp list`. A mismatch means someone else edited the layer since you read it — re-read, re-mint, retry; each nonce is good for exactly one write, so a retry always needs a new one. There is no "omit it for the first write" shortcut: writing into a settings file that does not exist yet means passing the empty-array hash.
- `hoody agent workflows delete` removes **user** workflows and saved customizations. A built-in/**system** workflow that you never customized is refused (`is_error:true`) and re-seeds on every boot; `hoody agent workflows hide` is the only way to remove it from view. Deleting your saved customization of a system workflow succeeds and brings the shipped version back: at once in a scoped realm, at the next daemon restart otherwise.
- Empty values on agent-profile edits mean *inherit / unrestrict*, not *clear to nothing*: `hoody agent definitions model set` with `model: ""` removes the model line (falls back to the default model), and `hoody agent definitions tools set` with `tools: []` removes the allow-list line, which means **all tools are allowed** (NOT zero). Pass a non-empty `tools` array to set the base allow-list. `hoody agent definitions tools set` takes only `tools` and `none`; to enforce the listed tools exactly, set `strict_tools: true` in the profile's frontmatter: read it with `hoody agent definitions source get`, add the key and write it back with `hoody agent definitions source set`. To give the profile no tools at all, pass `tools: []` with `none: true` (writes `tools: none`); `none: true` with a non-empty list returns `400 bad_request`. A profile with `strict_tools: true` is the exception: there an empty list grants only the benign special tools, never the full set.
- Prompting with no usable model/provider configured fails the turn. `hoody agent providers list` lists every catalogued provider whether or not it is set up, so check the one you intend to use with `hoody agent providers auth status` before you prompt (blocking or streamed): `ready` is true for a stored API key, a stored OAuth login, or a passwordless provider (`no_auth_ready`).
- A custom provider's `base_url` must be an `https` URL with no user name, password, query or fragment, at a public address. Create, and updates that change `base_url`, refuse one that is not (an internal address, or a name that resolves inside a network) with `422 provider_invalid` and `details.field` `base_url`. The destination is checked again when the agent connects, and a later refusal (a name that now resolves to an internal address) fails the model request instead, for example with `502 upstream_error` on a non-streaming completion. Create is not idempotent by itself: repeating a create that went through answers `409 provider_exists`, so send an `Idempotency-Key` to retry safely (the same key with another body is `422 idempotency_key_reused`). Deleting a provider (the result's `api_key_removed` says whether its stored key went too) leaves an open session on one of its models unconfigured: its next prompt fails with `session_unconfigured` until you switch it to another model, and agents and Jev settings that name one of its models fail the same way until changed.
- Speech calls answer `413 audio_too_long` for a wav or mp3 over 600 seconds (`413` too for a file over 16 MiB), `415` on a transcription for audio the model does not take, `422` when the model is unavailable or the input is refused, `502` / `504` for a provider failure or timeout, and `503` when speech is unavailable (`speech_unavailable`: speech is unavailable for this request; read `details.reason` when present: `no_credentials` means the selected model's provider has no key stored, `relay_*` means the voice relay could not serve it, and another speech model may still work) or busy (`speech_busy`: too many speech calls running on the agent, or, for a spoken Bot message, 4 recordings already being transcribed for that Bot) — honor `Retry-After`; resend a spoken Bot message with the same `Idempotency-Key` (an admitted message is not queued twice, but a failed transcription stored nothing, so the retry transcribes again; other speech calls do not deduplicate it: each retry is a new, billed call). A `429` is `rate_limited` (the per-client request rate; each non-streaming speech call also takes one of the client IP's completion slots and each open stream one of its stream slots), `speech_quota_exceeded` (the realm's, Bot's or agent's speech budget is spent for now) or, on a spoken Bot message, `idempotency_keys_exhausted` or `speech_busy` (too many requests waiting): read the code.
- Calling prompt/gate/cancel against a session whose live connection was torn down (`hoody agent sessions close`) returns not-found. If the record survives, re-attach with `hoody agent sessions create --attach-session-id <id>`; otherwise start a fresh session (the same create call without `attach`). After a *hard* delete (`hoody agent sessions delete`, which always erases the record) the record is gone and only a fresh session works.

## Related namespaces

`terminal`, `exec`, `files`, `notes`, `api` (its `botUrls` service gives a Bot a public URL).

## Examples

A **Bot** here is the agent's long-lived assistant (`hoody agent bots`). It opens delegate sessions on computers, follows them and reports back. Chat apps reach it as its channels; there is no separate `bot` namespace. Set `P`, `C`, `N` from `hoody computers get` first. The Bot's id below is `release-bot`; omit `id` on create to have one generated, and take it from the response.

### 1. Create a Bot, message it, follow its replies, forget, delete

**Goal:** run a Bot end to end. `guardrails` are limits on the work (they apply to the Bot and every delegate it opens), not instructions. A Bot lives in one realm: pick one with `X-Hoody-Realm` (`--agent-realm`), otherwise the agent's current realm is used. The Bot's own session opens when the first message is posted, or earlier on a spoken-message attempt (even one whose transcription then fails), so `session_id` is empty until then. A reset starts a new session at once, so read `session_id` again after one. This Bot has guardrails, so its default `guardrail_check` (`strict`) needs the guardrail checker (Jev), which needs the credential of the provider of `jev.model` when that provider is key-backed (`hoody-ai/hoody-decide` needs none). Hoody Decide is used only when `jev.model` names it; when `jev.model` is unset, Jev uses the default of a key-backed provider whose key is set. Without the key, every dispatch and delegate message is refused and the Bot says which key is missing; `lenient` still checks and refuses work that may break a guardrail, and lets the work go ahead unchecked only when the check cannot be made; `off` skips the check.

**Step 1 — create.** Send `id` to make a retry safe: a second create with the same id answers `409 bot_exists`.

```bash
hoody agent bots create --id release-bot --name 'Release bot' \
  --role 'Ships the weekly release.' --guardrails 'Never push to main.'
```

**Step 2 — message it.** The answer is `202` with `{message_id, state}`: `posted` (with `turn_id`) once dispatch is confirmed, `queued` when the message is accepted but dispatch is not yet confirmed. A busy Bot answers `queued` at once and the message goes out when its turn ends; a free Bot can also answer `queued` after a 3 second dispatch wait. Add an `Idempotency-Key` to retry safely.

```bash
hoody agent bots messages send --id release-bot --text 'Check the staging build and tell me if it is green.'
```

**Step 3 — follow the replies.** The stream carries finished log rows only: first a `state` frame (the Bot), then `row` frames, plus `lagged`, `archived` and `end`. The reply is one `bot` row written when its turn ends, and a turn with no reply text writes none. Resume with `since` (or `Last-Event-ID`). For live text, thinking and tool calls, follow the Bot's own `session_id` with `hoody agent sessions stream` instead. To read without streaming, page the log: pass `next_since` back as `since` while `has_more` is true.

```bash
hoody agent bots logs stream --id release-bot
hoody agent bots logs get --id release-bot --since 0
```

**Step 4 — forget or reset.** `hoody agent bots conversation clear` moves the log to the archive and clears the conversation; the Bot keeps its settings and delegates. `reset` also archives the log but starts a new session with the Bot's current model, which is how a changed `model` takes effect. The old session is not closed. Neither deletes the archive; `hoody agent bots archive clear` does.

```bash
hoody agent bots conversation clear --id release-bot --yes
hoody agent bots reset --id release-bot --yes
```

**Step 5 — delete.** Removes the Bot with its log and archive, after a best-effort stop of its working delegates. Its session and delegates are not closed: they stay listed under the sessions. Delegate sessions can be continued directly; to continue the former Bot session, fork it, because the Bot's own responder is removed with the Bot. To stop the Bot's running turn, cancel the Bot's `session_id` with `hoody agent sessions turns cancel --id <session_id> --turn-id <turn_id>` (there is no `bots` command for it), naming the `turn_id` that `hoody agent bots get` shows while `turn_running` is true. Only that turn stops: a late stop never stops a newer one, and delegates keep running (stop one with `hoody agent bots delegates stop`).

```bash
hoody agent bots delete --id release-bot --yes
```

### 2. Add a custom provider, store its key, use its model

**Goal:** connect an OpenAI-compatible endpoint and run a session on one of its models. The provider id below is `acme`; its model is selected as `acme/llama-3.3-70b`. Replace `https://api.acme.example/v1` (and `https://eu.api.acme.example/v1` in Step 4) with your provider's real https base URL: create resolves the host and refuses one that does not resolve (`422 provider_invalid`).

**Step 1 — create it.** `id`, `base_url` and `models` are required. Add an `Idempotency-Key` so a retry answers with the provider the first try created instead of `409 provider_exists`. The reply carries the provider, with each model's `spec`.

```bash
hoody agent providers create --id acme --endpoint https://api.acme.example/v1 \
  --models model=llama-3.3-70b,context_window=131072 --idempotency-key acme-create-1
```

**Step 2 — store its key.** The key has its own route and is never returned.

```bash
hoody agent providers apikey set --id acme --api-key "$KEY"
```

**Step 3 — use its model.** Start a session on it; `hoody agent sessions model set` switches an open one and `hoody agent definitions model set` pins an agent profile.

```bash
hoody agent sessions create --model acme/llama-3.3-70b
```

**Step 4 — change or remove it.** Update names only what changes (`models` and `headers` replace the current list and map; `id` and `model_prefix` are fixed). Delete asks for confirmation on the CLI and removes the stored key too when it is the one stored for this provider; `api_key_removed` in the result says whether it did.

```bash
hoody agent providers update --id acme --endpoint https://eu.api.acme.example/v1
hoody agent providers delete --id acme --yes
```

### 3. Speak a sentence, transcribe a recording, post a spoken message to a Bot

**Goal:** turn text into an mp3, turn a wav recording into text, then send that recording to the Bot from Example 1 as a spoken message (run step 4 before Example 1's step 5 deletes the Bot, or create it again with Example 1, step 1). Pick models from the list first: a text-to-speech model whose `formats` include `mp3` and a speech-to-text one, each with a provider key in place, and pass each as `model` (steps 2 and 3). A call without `model` uses settings `audio.tts_model` / `audio.stt_model`, and with neither set (and the Hoody AI relay default off) it is `422 speech_not_configured`; listing a model does not select it.

**Step 1 — list the speech models and one model's voices.**

```bash
hoody agent audio models list --capability tts
TTS_MODEL='<an id from that list>'
hoody agent audio voices list --model "$TTS_MODEL"
```

**Step 2 — speak a sentence.** The whole audio comes back in one answer; `response_format: 'mp3'` asks for mp3, and a model whose resolved formats lack `mp3` is refused `400`. Models served through the Hoody AI relay list an empty `formats` (it is resolved when the call is made).

```bash
hoody agent audio speech create --model "$TTS_MODEL" --input "The staging build is green." --response-format mp3 --out-file hello.mp3
```

**Step 3 — transcribe a recording.** One wav or mp3 file, at most 16 MiB and 600 seconds; `language` helps when you know it.

```bash
# A recording is a multipart upload, which has no CLI command: post it over HTTP to the kit URL.
K=$(hoody open agent --url)
K=${K%/}  # the printed URL ends in /
hoody agent audio models list --capability stt
STT_MODEL='<an id from that list>'
curl -sS -X POST "$K/api/v1/agent/audio/transcriptions" -F file=@question.wav -F "model=$STT_MODEL" -F language=en
```

**Step 3b — give the Bot a speech-to-text model (once; skip it when settings `audio.stt_model` is set).** The Bot's `speech` object replaces its speech settings whole (`null` removes them), so send every field you want to keep. A model that is unknown, lacks speech-to-text (`details.reason: "not_stt"`) or is not available is refused `422 model_unavailable`; nothing changes.

```bash
# `hoody agent bots update` has no flag for the speech object: send it over HTTP to the kit URL.
K=$(hoody open agent --url)
K=${K%/}  # the printed URL ends in /
curl -sS -X PATCH "$K/api/v1/agent/bots/release-bot" -H 'Content-Type: application/json' \
  -d "{\"speech\":{\"stt_model\":\"$STT_MODEL\"}}"
```

**Step 4 — post the recording to the Bot as a spoken message.** Same queueing as a text message (`202` with `state` `posted`, `queued` or `dropped`); a recording with no speech in it is answered `200 { no_speech: true }` and nothing is queued; an `Idempotency-Key` makes a retry safe. The form takes `file` and `language` only (another field is `400`): the Bot transcribes with its own `speech.stt_model`, else settings `audio.stt_model`, and with neither (and the Hoody AI relay default off) the call is `422 speech_not_configured`. Follow the reply as in Example 1, step 3.

```bash
curl -sS -X POST "$K/api/v1/agent/bots/release-bot/messages/audio" -H 'Idempotency-Key: q-2026-10-12-1' \
  -F file=@question.wav -F language=en
```

### 4. Give a Bot a public URL, hand out a key, call it, rotate, panic

**Goal:** let someone without a Hoody account talk to the Bot from Example 1 (run its step 1 first, or use any Bot of yours). A **Bot URL** is the Bot's public address, `https://<label>.hoody.bot`, plus named keys (`hbk_…`) you hand out; the URL belongs to your account, so you manage it with the `api` namespace and a Hoody login, while the person you share it with needs only the URL and a key. A Bot has at most one Bot URL, and everyone holding a key shares one conversation with the Bot (each caller appears to the Bot under its key's name). The work callers start is your Bot's work, at your cost. The project owner or an administrator can manage Bot URLs; a project member gets `403 BOT_URL_OWNER_ONLY`. Set `C` to the id of the computer whose agent runs the Bot (pass it as `hoody --computer "$C" …`, or export `HOODY_COMPUTER`, so every `hoody agent` command reaches that computer). The reference for the doors a caller can use (chat, Responses, Anthropic messages, MCP), the SDK caller client and the error codes is the `## Bot URLs` section of the appendix.

**Step 1 — read the Bot's reference.** The URL is bound to the Bot by the `realm`, `id` and `uid` the agent reports for it. A deleted and recreated Bot has a new `uid`, so a Bot URL never follows it: point it at the new Bot with `repoint`.

```bash
hoody --computer "$C" agent bots get --id release-bot -o json | jq '{realm, id, uid}'
REALM='<the realm it printed>'; BUID='<the uid it printed>'
```

**Step 2 — create the Bot URL.** Omit `label` to get a generated one (`hoody boturls label suggest` shows a free one without reserving it). A label is 8 to 48 characters of `a-z`, `0-9` and single hyphens, starting with a letter and ending with a letter or digit; every label ever used stays taken, even after its Bot URL is deleted. `bot.realm` must be `global` or a realm the computer belongs to. The URL starts with no keys, so nobody can call it yet; `cors` (default true) lets browsers call it. The answer carries `data.id` (`bu_…`) and `data.url`; `url` is `null` while the platform has no usable Bot zone, and create is refused then.

```bash
hoody boturls create --computer-id "$C" --bot-realm "$REALM" --bot-id release-bot --bot-uid "$BUID" --label release-bot-team
BU='<the bu_… id it printed>'
```

**Step 3 — wait until the change is applied.** Every write returns `propagation`; callers see a change about 11 seconds after `propagation.state` is `applied`, so poll `get` before you hand anything out, and again after you mint a key and after a rotate, revoke or panic (a new key does not work for its holder until then). `applied` covers publication only: a newly created or re-pointed Bot URL can take a little longer before its address resolves for callers, so after minting the first key check that `hoody boturls models list <url>` answers with that key before you hand it out, and retry if the name does not resolve yet. Deleting a Bot URL is the exception to polling: its reply is the only snapshot, and a later `get` answers 404 `BOT_URL_NOT_FOUND` at once, which does not mean the removal is applied. Poll only while the state is `pending`, with a bound: `failed` means publication encountered a failure; inspect `propagation.failed_count` and investigate rather than waiting indefinitely. The count can be zero when the intent has an error.

```bash
hoody boturls get "$BU" -o json | jq '.propagation.state, .data.status'
```

**Step 4 — mint a key for one person.** A key has a name (1 to 32 characters; unique on the Bot URL, and the Bot sees it as the caller's name), and optionally an expiry, an IPv4 allowlist and owner-only notes. The secret is in this answer only and cannot be read again: pass it to its holder over a private channel, never into a chat log or an issue. A Bot URL holds at most 20 live keys. A caller signed in with a login session, on an account that has 2FA with its API-key requirement on (the default), must also send a current 2FA code on key create and rotate (and on `repoint`, and on an `update` that turns the URL on, allows browser calls or frames, or changes its limits), else `400 OTP_REQUIRED`: pass `--otp-code <code>`. A code works once. A caller with an `hdy_` auth token needs no code.

```bash
hoody boturls keys create "$BU" --name Dana --expires-at 2026-12-31T23:59:59Z   # prints the secret once
```

**Step 5 — call it as the person you shared it with.** No Hoody login. Send the key as a bearer token (`Authorization: Bearer`). Over HTTP, a call with a key goes to `/v1/chat/completions` (any model name works; use the label), `/v1/responses`, `/v1/messages` or `/mcp`; `GET /` and `GET /SKILL.md` on the URL need no key and describe the doors. A long answer can take a while: the CLI and SDK `ask` wait for it, and the MCP `ask` over HTTP returns a `ref` to ask again with.

```bash
read -rs HOODY_BOT_KEY && export HOODY_BOT_KEY   # paste the key; it never goes on a command line
hoody boturls ask https://release-bot-team.hoody.bot "Is the staging build green?"
```

**Step 6 — rotate, revoke, panic, delete.** `rotate` keeps the key's id and settings and returns a new secret; the old one stops working for callers about 11 seconds after the change is `applied`; it needs the 2FA code under the same condition as key create (Step 4). `revoke` ends one key for good (a revoked key is gone, not paused; to pause a key use `update` with `enabled` false). `panic` is the emergency stop: in one step the URL is turned off and every key is revoked, while work the Bot already started keeps running (stop it in the agent). To reopen a panicked URL, turn it on with `update` (`enabled` true) and mint new keys. `delete` removes the URL; its label stays taken for ever. Deleting the computer detaches the URL (label and keys are kept, callers are refused) until you `repoint` it at a Bot in another computer.

```bash
KID='<the key id, bk_…>'
hoody boturls keys rotate "$BU" "$KID" -y    # prints the new secret once
hoody boturls keys revoke "$BU" "$KID" -y
hoody boturls panic "$BU" -y
```
