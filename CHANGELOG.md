# Changelog

All notable changes to `hoody-sdk` are documented here.

Format follows [Keep a Changelog](https://keepachangelog.com/) and [Semantic Versioning](https://semver.org/).

## [1.0.0-beta.15] — 2026-10-06

**Breaking: CLI and SDK names.** Every CLI command and SDK method now follows one vocabulary, and the old names are removed with no aliases or compatibility layer. [docs/MIGRATION-2026-10-NAMES.md](docs/MIGRATION-2026-10-NAMES.md) lists every old name beside its new one.

- The CLI reads `hoody <group> <noun> <verb>` with lowercase command words and no hyphens. `list` returns a collection and `get` one item; `create`, `update`, `set`, `delete`, `clear` and `purge` write. `toggle`-style commands became `enable` / `disable`. `run` waits for the outcome and `start` returns a handle. `stream` follows events and `connect` attaches a socket. `use` makes an item the current one.
- The SDK mirrors the CLI: `agent sessions model set` is `agent.sessions.setModel()`. Resources moved under their owner (`api.authTokens` is `api.auth.tokens`, `api.tfa` is `api.auth.twoFactor`, `api.proxyAliases` is `api.proxy.aliases`, rentals are under `api.servers`, container snapshot calls are `api.snapshots`), and `containers.manage(id, "start")` became `containers.start(id)`.
- Decisions: `agent definitions` replaces `agent agents`; pull requests are `prs` / `Pr`; `hoody logout` ends this device and `hoody logout --all` ends every session (`api.auth.logoutAll()`); `db`, `kv` and `upsert` keep their names.
- Removed: `hoody ps`, `ssh`, `pty`, `terminal sh`, `check-update`, `chatbot` and the `ls`-style aliases. Use `hoody shell`, `hoody containers list` and `hoody update`. Twenty-one group aliases were removed too (`hoody sqlite` is `hoody db`, `hoody notify` is `hoody notifications`, `hoody token` is `hoody auth`; the full table is in the migration guide). Flags keep their names and request and response fields are unchanged; where two old commands became one, the replacement takes a selecting flag (`hoody agent github commits create --push`, `hoody bot tokens revoke --all`, `hoody display mouse click --double`).

### Added

- **`share()` is exported from the package root.** `import { share, listShares, stopShare } from 'hoody-sdk'` (and `require('hoody-sdk').share`) now work like `mount`, as well as `hoody-sdk/share`. The root also exports `ShareError`, `AmbiguousShareError`, `UndeliveredWritesError` and the types `ShareOptions`, `ShareHandle`, `ShareTarget`, `ShareEvent`, `ShareState`, `ShareListEntry`, `ListSharesOptions`, `StopShareOptions` and `StopShareResult`. The browser entry does not export them.

- **Pipe live broadcasts (`?live`).**
  - `PipeStream.send()` / `receive()` and `PipeBrowser.receive()` take `live: true`. `live` with `n` above 1 or `sha256` throws a `RangeError` before any request.
  - `PipeMedia.shareScreen()` / `shareWebcam()` / `shareAudio()` take `live: true`: the upload goes to `?live`, the recorder is asked for a keyframe every 2 seconds, and `session.url` carries `live`. A live share needs a WebM recording and throws otherwise. `sendStream()`, `receiveStream()` and `receiveMedia()` take `live` too, and `getPageUrl('video', name, { live: true })` builds the live player link.
  - The CLI adds `--live` on `hoody pipe send`, `receive` and `url get` (with or without `--video`). `--live` with `-n` above 1, `--sha256` or `--browser` exits 1 before any request.

- **Pipe `status()`, `?wait`, `?sha256` and metrics.**
  - `PipeStream.status(path, { transfer? })` resolves to the kit's `?status` snapshot of a name, or of one transfer. `PipeStream.metrics()` resolves to the kit's Prometheus text.
  - `send()` and `receive()` take `wait` (1-3600 seconds; any other value throws `RangeError` before the request) and `sha256`.
  - `send()` returns `sha256`, a promise of the kit's digest of a completed transfer, or null.
  - `receive()` returns `transferId`. With `sha256` it also returns `verified`: it resolves to the digest once the body read to the end matches the kit's record of that transfer. It rejects with `PipeIntegrityError` (`mismatch`, `unavailable`, or `incomplete` when the body is cancelled or the signal aborts first), or with the body's own error, and it is never an unhandled rejection.
  - The `done` progress event (PipeStream and PipeBrowser) carries `sha256` and `transferId` when the kit sends them.
  - The CLI adds `hoody pipe status`, `hoody pipe metrics`, and `--wait` / `--sha256` on `send` and `receive` (`receive --sha256` exits 1 when the check fails and keeps the output). `url get` takes `--wait`, `--sha256` and `--status`, and `--wait` no longer needs `--ws`.

- **`files.readText()`, `files.readJson()` and `files.readBytes()` return the file content itself.** `readText(path)` resolves to the string, `readJson(path)` to the parsed value and `readBytes(path)` to a `Uint8Array`, with no `{ statusCode, message, data }` envelope. They take the options of `files.get` (such as `revision` or `lines`) and set the decoding themselves. `readJson` fetches the text and parses it, so a file that looks like an envelope is read as the file; content that is not JSON rejects with a `SyntaxError` that names the path. A missing file rejects with the `ApiError` of `get` (status 404). `files.get` is unchanged.

- **`sqlite.sql.query()` and `sqlite.sql.run()` run one SQL statement.** `query({ db, sql, params })` resolves to `{ rows, columns, truncated }` and suits any statement that returns rows, a write with `RETURNING` included; `run({ db, sql, params })` resolves to `{ rowsUpdated }`, and a write with `RETURNING` to `{ rowsUpdated, rows }` (the rows it returned, one per changed row; `truncated: true` when the kit stopped at its row cap). Both send one item through `sql.runTransaction` (`POST /api/v1/sqlite/db`) and return plain values. `params` is an array for `?` placeholders or an object for `:name` ones (`values` is accepted as the same thing). `db` is required; `create_db_if_missing`, `timeout` and the request options pass through. A missing `db` or `sql` throws a `ValidationError` before any request; a kit error rejects with its `ApiError`. `sqlite.sql` is still the same `SqlService` object, and `queryReadOnly` is unchanged.

- **`sqlite.kv.read()` returns the stored value itself.** `read(key, { db })` resolves to the value as stored: the parsed JSON for a JSON value, a string for text, an `ArrayBuffer` for bytes, with no `{ statusCode, message, data }` envelope, so a stored object with its own `data` key comes back as stored. It takes the options of `kv.get` (`table`, `path`, `at_timestamp`, request options) and sets the decoding itself. A missing key rejects with the `ApiError` of `get` (status 404). `kv.get` is unchanged.

- **The KV key calls also take one object.** `kv.get({ db, key })`, `set({ db, key, value, ...options })`, `delete({ db, key })`, and `exists`, `increment`, `decrement`, `pop`, `listHistory`, `rollback`, `getSnapshot`, `push`, `remove` and `read` the same way, send exactly the request of the positional call, which is unchanged. For `remove`, `value` is the element to remove: `remove({ db, key, value })` sends the kit's `{ value }` body (an explicit `null` included), and `remove({ db, key, index })` sends none. Per-call template variables go second. The object form leaves out `rawResponse` and `responseType` (pass those positionally); a missing key, a missing `value` for `set` or `push`, or either shape option is a `ValidationError` before any request. `list` and the batch calls keep their shapes. The object form is typed on the client's `sqlite.kv` (the exported `SqliteKvStore` type, assignable to `KvService`); `KvService`'s own method types are unchanged, so a subclass that overrides a KV method with the positional signature, and a mock typed from the class, compile as before.

- **Event streams carry their response.** Every event-stream method returns a stream with `response`: the status, the headers, and the headers the operation documents under their parameter names (`agent.sessions.startTurnAndStream()` gives `response.documented.XHoodyTurnId`). Reading `response` sends the request if the loop has not started yet, so `await stream.response` before `for await` works. `stream.return()` and `stream.throw()` cancel the body at once, even when a read is waiting on a server that sends nothing.

- **`agent.sessions.stream()` attaches to a session over fetch.** It is the server-sent-events form of `agent.sessions.connect()`, with the same `since`, `incarnation` and `Last-Event-ID` resume, and it yields the gateway's control frames (`replay_boundary`, `lagged`) as frames.

- **A frame size limit for event streams.** `maxStreamFrameBytes` on the client (16 MiB by default) and `maxFrameBytes` on a call bound one frame; a larger one ends the stream with an `ApiError` of code `STREAM_FRAME_TOO_LARGE`. Only a whole number above 0 is used; anything else keeps the default.

- **`exec.connect(url, { token })` connects to a live exec script.** It returns a connection with `capabilities()`, `send(message)`, `call(name, args)`, `eval(expression)`, `evaluate(fn, args)` (the script calls `fn(ctx, ...args)`), `events()` and `attach()`, on the script's own URL (a full URL, or a script path on the box's exec kit). Each op sends the `X-Hoody-Remote` header, and the script token travels in `X-Token`, never in the URL. Events are an SSE stream by default. `ws: true` carries send, call and events over one `hoody-remote.v1` WebSocket, which takes the token as a `hoody-token.*` subprotocol entry. `eval` is always a one-shot POST. Every op returns the server's full answer object, so an eval's value is `(await conn.eval('x')).result`. A refusal is raised as an `ExecRemoteError`, or as the subclass for its cause: `ExecRemoteTokenError`, `ExecRemotePermissionError`, `ExecRemoteThrewError`, `ExecRemoteTimeoutError`, `ExecRemoteUnsupportedError` or `ExecRemoteConnectionError`. Each carries the server's `code`, `layer` and `fix` (the magic comments to add and the `magic-comments/update` call), and its message includes the fix lines. A live session the script stops admitting (its token removed or narrowed, or the permission switched off) ends `events()` and the attach socket with that typed refusal; it is never reopened on its own. The server side needs a hoody-exec with remote ops; an older one is reported as `ExecRemoteUnsupportedError`.

- **`hoody exec remote <url|path> <op>`** runs the same ops from the CLI: `capabilities`, `send`, `call`, `eval` (`--target`, `--start`, `--file`), `events` (`--tail <level>`, `--count`, `--timeout`, NDJSON output) and `attach` (each stdin line is sent). The script token is read from `--remote-token`, `--remote-token-file <path|->` or `HOODY_EXEC_REMOTE_TOKEN`; the global `--token` stays the account token. A refusal prints the fix on stderr, and the exit code names the cause: 3 for a permission (a capability that is off, or a token without the op's scope), 4 for a missing or wrong token, 5 when the script threw, 124 for a timeout.

- **Every generated method takes per-call `headers`.** Pass them on the same options bag as `signal` and `timeoutMs`: `files.get(path, { headers: { Accept: 'text/plain' } })`. A header parameter the operation declares (such as `If-Match`), when you pass it, wins over the same name in `headers`, in any case. A `Content-Type` in any spelling replaces the default instead of adding a second one. `Authorization`, `X-Hoody-Client-ID` and `X-Hoody-Client-Name` are set by the client, so passing one of them throws a `TypeError` before any request; use a separate client for another token.

- **CLI: `hoody files uploads unreadable list` and `unreadable delete <id>`**, for the stored records of unsent files the file service cannot read; while one exists, a mount or backend delete cannot confirm that nothing was left unsent. **`hoody terminal system displays stop <display>`** stops an X display a deleted terminal session left running.

- **`hoody code status` and `hoody code version`.** `status` returns the orchestrator's configuration and one entry per running editor instance, with its id, port, folder and uptime — the way to learn which instance numbers exist. `version` reports the orchestrator binary and the packaged editor tree separately, because they are built and deployed separately, and never contacts the network.

- **Hoody Run is a full command group: `hoody run …`.** Bare `hoody run <app>` still resolves an app to its exact shell command, and the kit's own surface is now 28 commands beside it. `run search` queries the package sources page by page with a cursor, `run test` plans a run and reports the command, the missing requirements and the effective policy, `run resolve` is the raw resolver call for a query the bare form cannot express (given a launch path such as `linux/nix/gui/firefox`, it resolves that path), and `run config get` and `run health` read the stored configuration and the kit health. `run jobs search create` starts a background search and `run jobs get` follows it. `run sources list|create|update|delete|sync|diagnostics get` manage the package sources, including per-source runtime health. `run profiles list|create|update|delete|use` manage the named defaults applied to searches and runs. `run recipes list|get|create|update|delete|search|resolve` manage saved launch recipes and resolve one to a command.

- **Hoody Notes gains ten commands.** `notes doc append` adds to a document without rewriting it, `notes doc export-ticket` mints a one-shot export ticket and `notes doc block-svg` renders one block as SVG. `notes node mark-seen` and `notes node mark-opened` record the two read states a client reports, `notes comment reanchor` re-binds a comment whose anchor drifted, `notes avatar upload` and `notes avatar download` manage a notes identity's picture, `notes user invite` creates the notes-side users an invitation needs, and `notes health` is the kit health check.

- **The account and sign-in surface is reachable from the CLI.** `hoody auth config get` reads the OAuth configuration, and `auth oauth authorize`, `oauth exchange` and `oauth intents cancel` drive a browser OAuth flow end to end; `auth device start` and `auth device poll` drive the device flow for a machine with no browser. `auth tokens templates list` lists the permission templates a token can be created from, `auth claims create` issues an identity claim, and `auth waitlist join` / `waitlist update` cover the waitlist. `hoody users free tier status`, `users security history list` and `users onboarding milestones complete`, `hoody inbox summary` (unread counts and the latest accessible notification), `hoody meta social stats`, and `hoody wallet github bonus status` / `github bonus claim` complete the account-level reads and the GitHub star bonus.

- **Server offers and reservations: `hoody servers offers list`, `offers reserve`, `reservations list`, `reservations get` and `stats`.** The offer catalogue, a reservation against one of its offers, the caller's own reservations, and the runtime state of a rented server.

- **Smaller gaps across four kits.** `hoody files mkdir` creates a directory and `files whoami` reports the identity the file kit sees; `hoody browser viewport get` and `viewport set` read and set a tab's viewport; `hoody terminal processes pause` and `resume` suspend and resume a process, and `terminal sessions mouse send` sends mouse events to a session; `hoody curl jobs stream` follows a job's events as they happen and `hoody exec scripts stats list` lists the scripts a container monitors.

- **The `bot` namespace ships: `client.bot.*` and `hoody bot …`.** The bot kit serves chat-channel registrations, and the whole management surface is now generated — 18 methods over `/api/v1/bot`. `hoody bot create` stores a channel token (encrypted at rest) and returns the registration; `hoody bot list`, `get` and `delete` manage them; `hoody bot start` and `stop` control long-polling. `hoody bot policy get` / `update` read and write a registration's mode and allowlists, `hoody bot profile update` publishes the bot profile (name, descriptions, default admin rights) to the channel, and `hoody bot commands sync` publishes the registered command list and returns the channel's readback. `hoody bot logs list` returns the redacted audit log newest-first and `hoody bot logs purge` deletes rows older than a cutoff, never inside the retention window. `hoody bot sessions revoke <registration> <channel-user>` ends one chat user's login and `hoody bot tokens revoke` ends every one for a registration. `hoody bot health` is the unauthenticated nine-field kit health, `hoody bot manifest get` returns the chat manifest the build is pinned to as it was baked, and `hoody bot keys rotate` re-encrypts every sealed column under a new kit key.

- **`hoody agent github` covers the repository workflow.** Thirteen operations that existed only inside the agent are now SDK methods and CLI commands: `branches create` and `branches use`; `diff` for the working tree; `repos resolve`, which resolves the bound repository's owner and name; `issues list` and `issues create`; `commits list` for recent commit history; `prs list` and `prs checkout`; `stash push` and `stash pop`; and `worktrees list` with `worktrees create`. They join the `commits create`, `status`, `sync` and `prs create` commands that were already there, so a repository can be driven end to end without leaving the CLI.

- **`hoody agent memory` exposes the memory subsystem's own controls.** `memory status` reads the subsystem's state. `intents create` mints the single-use intent a guarded write requires; the intent binds `{store, op, project}` and the realm that was active when it was minted, is spent the moment it is checked, and expires, so mint it when you submit rather than when a form opens. `projects delete` spends such an intent: it erases everything a project owns — observations, memories, summaries, sessions, lessons, slots, documents, embeddings, search postings, the relation graph and provenance, plus the registry row, the profile cache and the consolidation cursor — and the CLI asks for a typed confirmation first.

- **A session's approval policy, its approver lease and its turn receipts are addressable.** `hoody agent sessions approval get` and `update` read and set the session's mode (`default` or `always`) and its lock; `rules set` and `rules delete` manage one per-tool rule. Answering a gate needs the approver lease, which `hoody agent sessions approver lease claim` mints, `renew` extends and `release` hands back; a lease is bound to the session, the daemon execution epoch, the holder and a generation, so a daemon restart invalidates every one of them. `hoody agent sessions attachments claim` holds a live session and its parked gate alive between turns, with `renew` and `release` on the lease it returns. `hoody agent sessions snapshot get` reads a session's recoverable state, `yolo set` arms or disarms auto-approve, and `sessions turns list` / `turns get` / `turns create` read and dispatch durable, retry-safe turn receipts.

- **`hoody agent version` and `hoody agent whoami`.** The first reports the agent API version and the capabilities this build serves; the second reports the Hoody platform identity the agent is running as and the realm scope it resolves to.

- **Proxied-usage documents and the public configuration are readable.** `hoody containers proxy usage <id> --from <YYYY-MM> --to <YYYY-MM>` and `hoody projects proxy usage <id> --from <YYYY-MM> --to <YYYY-MM>` return the proxied-usage documents for one container or for every container in a project, over a window of at most twelve months. `hoody meta config get` returns the public configuration Hoody publishes and `hoody meta config values get <key>` returns one value from it; both are unauthenticated routes.

- **`hoody browser snapshot get`, `browser act` and `browser wait`.** The observe-act-wait triple a caller driving a browser needs: `snapshot get` returns an accessibility snapshot of a tab with element refs, `act` performs a native element action against one of those refs, and `wait` blocks until a condition in the tab holds.

- **`hoody display windows restore`** un-minimizes a window, completing the window verbs beside `focus`, `raise`, `minimize`, `move`, `resize`, `close` and `search`.

- **Topping up a wallet is a CLI flow.** `hoody wallet payments availability get` reports which providers are open to this account, the amount bounds and whether AI transactions are enabled. `hoody wallet payments stripe checkout create` starts a card payment and `hoody wallet payments crypto invoices create` starts a hosted crypto invoice; `hoody wallet payments stripe intents list` / `intents get <id>` and the matching `crypto` pair follow an intent to settlement. The routes were already in the API and the SDK; none of them had a command.

- **`hoody db health`, `cache stats` and `maintenance run`.** The sqlite kit's health check, its cache-health snapshot and its maintenance runner, which had SDK methods and no CLI commands.

- **`hoody db list`** lists the databases under a directory (`GET /api/v1/sqlite/db/list`), which previously had an SDK method and no CLI command.

- **Fourteen `hoody agent` commands for SDK methods that had none.** `hoody agent jev models list`, `settings get`, `settings update` and `test`; `github commits create`, `commits message suggest`, `branches delete`, `prs merge`, `worktrees delete` and `repos credentials set`; `agent sessions rename`; `workflows start` and `workflows summary set`; and `realms use`. `branches delete`, `prs merge` and `worktrees delete` ask for confirmation (skip it with `-y`). `agent.jev.decide()` stays SDK-only: its questions are nested objects no flag can carry.

- **Eight commands for the new SDK methods.** `hoody curl schedules update`, `hoody daemon programs logs stream`, `files downloads cancel`, `files extractions cancel`, `db delete`, `watch update`, `run jobs list` and `run jobs cancel` reach the methods listed under New SDK methods below. `hoody files get --thumbnail-format` picks a thumbnail's output image format. It and the other thumbnail options are sent only when given, so a plain `files get` sends no image parameters.

- **A program's sandbox can be set, cleared and inspected from the CLI.** `hoody daemon programs create` and `hoody daemon programs update` take the block one field at a time: `--sandbox-filesystem-read-only-root`, `--sandbox-filesystem-writable`, `--sandbox-filesystem-hidden`, `--sandbox-network-mode`, `--sandbox-network-bind-ports`, `--sandbox-network-connect-ports`, `--sandbox-network-ingress-allow-from`, `--sandbox-network-ingress-allow-platform`, `--sandbox-network-ingress-rate-limit`, `--sandbox-process-max-memory`, `--sandbox-process-max-pids`, `--sandbox-process-max-open-files` and `--sandbox-process-private-tmp`. They replace the three `--sandbox-filesystem`, `--sandbox-network` and `--sandbox-process` flags, which each took a hand-written JSON object. Port lists accept single ports and `a-b` ranges together (`--sandbox-network-bind-ports 8000-8003,443`); a plain number is sent as a number, which the daemon's port grammar requires, and a range as a string.

  `hoody daemon programs sandbox get <id>` reaches `daemon.programs.getSandbox()`. The result is the stored block as persisted, the 12-hex-digit policy revision, the `bwrap` and `systemd-run` argument vectors the policy resolves to, the nftables table and chain the kernel is holding, and a `firewall` verdict of `ok`, `degraded`, `draining` or `none`. `problems` carries one line per reason the verdict is `degraded`, including the case where an earlier definition of the program may still be running unconfined, which keeps its firewall records and its reserved ports until the daemon measures that nothing runs under the old group names.


- **`display.windows.wait()` waits for a window to appear or disappear.** `POST /api/v1/display/input/wait-until`, reachable from the CLI as `hoody display windows wait`. A `window-present` wait ends once at least one window matches an extended POSIX regex, matched against the title, the class, or the classname; a `window-absent` wait ends when the last match goes away, or when a window named by id stops existing. It removes the reason to poll `window/search` over HTTP while an application starts up or a dialog closes.

  A condition that stayed false for the whole budget answers 200 with `timedOut: true` rather than an error, so an expired wait is control flow and a failure to observe the display is still reported as a failure. `timeoutMs` is capped at 25000, below the 30000 ms transport default the SDK and the CLI both use, so the server budget cannot outlast the client's own request timeout. `pollMs` sets the observation interval and must not exceed the timeout. The result reports `waitedMs`, the number of completed `polls`, and the window ids that matched.

- **`input.mouseScroll()` takes a pointer position and a wheel delay.** `x` and `y`, which must be given together, scroll at that point instead of wherever the pointer happens to be, and the move and the wheel events go out as one chained call so nothing can move the pointer in between. `delay` sets the milliseconds between wheel clicks, against the same 4000 ms `clicks` x `delay` budget the kit already enforced.

- **`input.clickAt()` takes `repeat` and `delay`.** `repeat` clicks at the point in one chained call, so the pointer cannot be moved between the clicks, and `delay` is the pause after every click including the last. A double-click is `repeat: 2` with a `delay` under the desktop's double-click time.

- **Batch and act results carry what an action read back.** `BatchResult.completed[]` and `ActionWithScreenshotResult.action` gain `result`, present for `clipboard/read`, `window/focus`, `window/restore` and `window/search`, and absent for actions whose only outcome is that they happened. The eight window actions (`window/focus`, `raise`, `minimize`, `restore`, `move`, `resize`, `close` and `search`) are now dispatchable through `input.act()` and `input.batch()`, so a sequence no longer has to leave the batch to focus or resize a window. `input.act()` documents the `404` a missing target window produces.

- **`screenshots.capture()` takes `region` and `cursor`.** Both query parameters were already live on `GET /api/v1/display/screenshot` but undocumented, so neither the SDK method nor `hoody display screenshots capture` exposed them. `region` crops the returned image to `x1,y1,x2,y2` in capture coordinates, which are the bounding box of the composited windows rather than root-window coordinates. `cursor` adds the pointer position to the base64 JSON form; a binary PNG response has nowhere to carry it.

- **Pending uploads can be listed, inspected, delivered, stopped and discarded.** Files a mount could not finish uploading — after a crash, a stop, or while they are still uploading — are held as pending uploads. Six operations under `files.uploads` cover them: `files.uploads.list`, `listFiles` (one page at a time, with `next_cursor`), `download`, `deliver`, `stop` and `delete`, and in the CLI `hoody files uploads list`, `files list`, `download`, `deliver`, `stop` and `delete`. A held file is named by `path_b64`, and by `path` when its name is valid UTF-8; `path_display` is for reading only and is accepted nowhere. `deliver` overwrites newer versions on the backend and `delete` deletes the only copy of the held files, so both ask for confirmation. `download` prints the file as text: use the SDK or the HTTP API for binary files. A pending upload reports why each file was held, including `changed_on_storage`, `check_failed` and `cannot_verify`, and lists `unknown_holders`; a delivering item can be stopped.

- **Mounts report their held files and can upload them automatically.** Mount responses gain `auto_deliver`, `pending_uploads`, `status_message` and `delivery`, and backend responses gain `pending_uploads`. `hoody files mounts create` takes `--no-auto-deliver`, and `hoody files mounts list` and `get` show the status message and the number of files waiting to upload.

- **`notes.files.upload()` uploads a file into a notebook in one call.** It creates the file node, then sends the bytes over TUS in chunks, with an optional `onProgress` callback. `resumeUpload()` continues an interrupted upload from the offset the server holds, `uploads.getOffset()` reads that offset and `uploads.cancel()` abandons the upload. A failure the helper detects itself carries a `NOTES_UPLOAD_*` code. `generateNotesFileId`, `encodeTusMetadata` and `NOTES_UPLOAD_CHUNK_BYTES` are exported for callers that drive TUS themselves.

- **Session control on `HoodyClient`.** `setSessionToken(token)` sets the token of every client in the session. `adoptSession(tokens)` adopts a session issued outside `login()`, such as the result of `api.auth.twoFactor.verify()` or `api.auth.oauth.exchange()`, and keeps its refresh token for automatic refresh. `completeTwoFactorLogin(tempToken, code)` finishes a two-factor login on the client. `HoodyClient.authenticate()` rejects a two-factor account with a `TwoFactorRequiredError`, and `await err.complete(code)` resolves to the signed-in client. `logout()` calls the API's logout, which ends every session of the account, and clears the credentials of every client in the session.

- **Middleware can check response signatures.** `captureRawBody: true`, on the client or on one request, gives `onResponse` the exact response bytes as `ctx.rawBody`, and `verifyHoodySignatureFromContext(ctx, publicKey)` checks the `X-Hoody-Signature` header against them.

- **New exports and options.** `TwoFactorRequiredError`, `isRealmScopeError`, `HttpClient`, `pipeTransportFromClient` and `withTokenQueryParam` are exported from the package root and the browser entry, as are `verifyHoodySignatureFromContext` and `hoodySignaturePath`, and every generated request and response type can be imported type-only. A Kit token credential takes `param` to travel as a query parameter instead of a header, WebSocket upgrades included. Generated methods take a per-call `cache` option.

- **New SDK methods.** `sqlite.databases.delete()`, `files.downloads.cancel()`, `files.extractions.cancel()`, `watch.watchers.update()`, `run.jobs.list()` and `run.jobs.cancel()`, `curl.schedules.update()` and `daemon.programs.streamLogs()`. `listAll()` and `listIterator()` are generated for the paged notes listings (`notes.nodes.list()`, `notes.nodes.listChildren()`, `notes.comments.list()`, `notes.comments.listAnchors()`, `notes.versions.list()`) and for `sqlite.history.list()`.

- **`hoody.events`: real-time events with recovery.** Each client has a lazily opened event stream. `on(pattern, handler, { filter, includeEphemeral, signal })` handles one type, a list, a dotted prefix such as `'container.*'` or `'container.snapshot.*'`, or `'*'`. `waitFor(pattern, filter, action, { timeoutMs })` runs `action` only after the stream has caught up, so the event it causes cannot be missed. `prepareWait` is the two-step form. `stream({ types, after, filter, maxBytes, onGap, signal })` is an async iterator; each event it yields carries `resume_after`, an at-least-once resume point to save and pass back as `after` (an event's own `cursor` is not a resume point). With `after`, it yields the missed history first, in order, and holds live events behind it. Each transient history retry is reported through `onState` as an `EVENTS_HISTORY_RETRY` notice with `attempt` (per page, from 1) and `delayMs`. `bootstrap(readFn)` returns your GET snapshot together with the resources that events touched while it ran; it holds the connection for its whole run, so it needs no other subscriber. `ready()`, `onState()`, `state` and `close()` complete the surface; `ready()` holds the connection only while it waits. After a disconnect the stream reconnects with its own backoff (1 s to 30 s), reads what it missed from `GET /api/v1/events?after=<cursor>`, and delivers it with `replayed: true`, once per subscription. When continuity cannot be restored (an expired or invalid cursor, deleted history, or more than 20 pages missed), it resumes from the current boundary and reports `{ kind: 'gap', reason }` through `onState`. `stream()` marks the first event after any loss with `gap_before: { reason, dropped? }`, including a loop that fell more than `maxBytes` (default 8 MiB) behind and lost its oldest buffered events; `onState` reports such a stream-only gap with `stream: true`. `activity.logged` is live only: wildcards skip it unless `includeEphemeral` is set. A realm-restricted token needs a `withRealm()` client: without one the stream is refused with `REALM_REQUIRED`. `logout()`, `login()`, `adoptSession()`, `setToken()`, `setSessionToken()` and a direct `api.auth.logoutAll()` end the stream's session; pending waits reject with `EventsSessionChangedError`, and handlers reconnect once the new session has a token. Errors are `EventsError` subclasses: `EventsAuthError`, `EventsClosedError`, `EventsSessionChangedError`, `EventsTimeoutError` and `EventsGapError`. `examples/events-watch.ts` prints a filtered feed as NDJSON.

- **A typed event catalog.** `EVENT_TYPES`, `EVENT_CATALOG`, `isEventType`, `isEventPattern`, `expandEventPattern` and `eventCatalogInfo` are package-root exports, with the types `EventType`, `EventPattern`, `HoodyEventMap`, `EventPayload<T>` and `ResourceTypeFor<T>`. Names and payload types come from the server's catalog, vendored as `lib/events-catalog.json`. A misspelt type or prefix is a compile error, and a `TypeError` at runtime. Reserved names, which the server declares but never emits, stay in the catalog so code that names them keeps compiling; each is marked `Reserved: declared but not emitted by the server` in its JSDoc, and `isReservedEventType()` identifies them. The new types include `container.updated`, `container.paused`, `container.operation.completed` and `.failed` (matched to the `operation_id` a start, stop, copy or sync returns; `.completed` means exit code 0), `container.network.*`, `container.env.*`, `project.permission.*`, `vault.*`, `pool.created`/`updated`/`deleted`, `account.updated`, `server.deleted`, `server.rental_*`, `server.command.*`, `server.reservation.*`, `server.offer.*`, `billing.*` and `image.library.added`.

- **`hoody events stream` and `hoody containers wait`.** `hoody events stream` streams events as NDJSON on stdout, one event per line, with connection state, retries and errors on stderr. It takes `--type` (repeatable; a type or a pattern such as `container.*`), `--project-id`, `--container-id`, `--resource-id`, `--since <resume_after>` to resume from the `resume_after` of the last line handled (never its `cursor`: an event recovered from history can arrive after later ones; resuming may repeat events, so de-duplicate by `id`), `--once`, `--timeout` (a duration such as `120s` or `5m`) and `--include-ephemeral`. Without `--since` it starts with events committed from now on. `containers wait <id> --state running|stopped|paused|failed [--timeout 120s]` exits at once when the container is already in that runtime state (not application readiness), otherwise re-reads it on each of its change events, and prints the result as JSON. Exit codes: 0 satisfied, 124 timeout, 3 continuity lost (`hoody events stream --once`), 4 refused or revoked, 130 interrupted, 1 anything else. The CLI package now depends on `socket.io-client` ^4.8.3.

- **Embed URLs for every kit UI: `client.embeds`.** `client.embeds.<kit>.<view>(container, opts)` returns the URL of one page of a kit's browser UI, ready to open or put in an iframe: 46 views across 18 kits, from the file editor and a terminal session to the cron manager and the SQLite studio. Each view is a typed function whose options are that view's parameters; `client.embeds.url(kit, target, opts)` is the untyped form, and `views(kit)` and `catalog()` list what exists. On a `withContainer()` client the container can be left out. The host comes from the client's own `getKitUrl()`, so an embed URL and a kit API call address the same host. On a kit's own views, a parameter that writes or runs something, a value the edge sets from the hostname, or an index outside the published bounds throws `EmbedValidationError`, whose `code` names the rule. The parameter refusals do not cover three views: `http.content` and `https.content` pass any query to your own application, and opening `exec.script` runs your script with the query it carries. The views that work under a proxy alias take the alias as their target. `buildEmbedUrl`, `getEmbedCatalog`, `listEmbedViews`, `deriveContainersDomain`, `createEmbeds` and `patchEmbedsPrototype` are exported from the package root and the browser bundle for code without a client.

- **The embeds construction catalog ships with the package.** `generated/embeds.catalog.v1.json` lists every view with its path, its parameters, the parameters it refuses and why, whether it can be framed, and whether it accepts an alias. `getEmbedCatalog()` returns the same data, and the docs site publishes the file at `/embeds/catalog.v1.json` beside the embed URLs guide (`/guides/embed-urls/`).

### Changed

- **`embeds.terminal.session` description:** a terminal that belongs to a daemon program attaches to that program and never starts a shell.
- **`embeds.terminal.session` and `embeds.agent.webui` take `title` and `rendererType`.** `title` sets the browser tab title (HTML tags are removed). `rendererType` picks how the terminal is drawn: `webgl` (the default; Firefox uses `dom`), `dom`, or `canvas` (drawn with WebGL); phones, tablets and other touch-screen devices use `dom` whatever is asked; try `dom` when text renders wrongly with WebGL on a particular browser or GPU. A value outside the enum throws `EmbedValidationError`. Both were refused until now because the terminal's own preferences replaced them on connect; the terminal UI now keeps the URL value The catalog and the docs tables list them, and `hoody terminal open` and `hoody agent open` take the flags.

- **`exec.run()` accepts one leading `/`.** `exec.run('/health')` calls the same script as `exec.run('health')`, as the path reads after the exec origin in a URL. Every other check stays: `//host/x`, a percent-encoded `/` at the start, and `.`/`..` segments are still refused.

- **`new HoodyClient({ token })` off a web page reaches the public API.** Without `baseURL`, a client in Node, Bun or an exec script took the empty base and every `api.*` call failed with "fetch() URL is invalid". It now takes `HOODY_BASE_URL`, else `HOODY_API_URL`, the variables the CLI reads, else `https://api.hoody.com`; that base is the account API unless `target` is given, and a `target: 'kit'` client gets no built-in host. A realm requested on such a client goes to that API's realm host. On a page an omitted base is still the page's origin, and so is a worker's: an http(s) `document.baseURI`, `location.href` or `location.origin` (a `blob:` worker has only the last) counts, the same rule the transports resolve a relative URL by. A given `baseURL` is never changed.

- **Reading a namespace off an un-awaited `withContainer()` throws.** `hoody.withContainer(c).sqlite` (no `await`) read `undefined` and failed later with "undefined is not an object"; it now throws an `Error` that names the missing `await`. The returned promise is otherwise unchanged.

- **Event-stream errors are fixed text.** `streamEvents()` and every event-stream method raise, and reject `response` with, an error that holds only a fixed code (`STREAM_REQUEST_FAILED`, `STREAM_READ_FAILED`, `STREAM_HTTP_ERROR`, `NOT_AN_EVENT_STREAM`, `ABORTED`, `ETIMEDOUT`, `REDIRECT_REFUSED`, `STREAM_FRAME_TOO_LARGE`), a fixed sentence and the HTTP status; an abort is an `AbortError` with a fixed message, whatever reason the signal was given. A server's error message and body, a transport exception's message and an abort reason no longer appear on it: the original error goes to `options.onDiagnostic`, once per failure. A 2xx that is not an event stream (a `202 { job_id }` job acknowledgement) is `NOT_AN_EVENT_STREAM`, and its body is on the error `onDiagnostic` receives.

- **Closing an event stream before its headers aborts the request.** `stream.return()` or `stream.throw()` while the request is still in flight aborts it, and the client's `onError` middleware then sees an `ABORTED` error, as it does for a caller's abort. The iteration itself just ends, and `onDiagnostic` receives nothing.

- **Breaking: remote backends no longer take credentials from the server's own environment.** The files service accepts only explicit credentials, and the create methods' types now say so: `files.backends.createS3`, `createDrive`, `createGoogleCloudStorage`, `createQingstor` and `createSwift` accept `env_auth` only as `false`; `createAzureblob` accepts `env_auth`, `use_az` and `use_msi` only as `false`, and `createAzurefiles` `env_auth` and `use_msi`; `createOracleobjectstorage` accepts only `provider: "no_auth"`, which is now its default (it was `env_auth`). Pass the backend's own keys, token or account instead.

- **Breaking: `files.backends` create types follow the files service's rclone v1.75.1.**
  - Removed, and refused with 400: `createAzurefiles` `connection_string`, `createHdfs` `service_principal_name`, `createOracleobjectstorage` `config_profile` and `createWebdav` `unix_socket`.
  - Now required: `createIclouddrive` `service` (`drive` or `photos`), `createLinkbox` `email` and `password` (with `token`), and `createSia` `api_url`, which has no default.
  - No longer required: `createMega` `pass` and `createS3` `endpoint`.
  - `createAzureblob` and `createAzurefiles` accept `use_emulator` only as `false`, `createAzurefiles` also `use_az`, and `createSmb` `use_kerberos`.
  - Many create methods take options new in rclone v1.75.1, among them `createS3`, `createDropbox`, `createZoho` and `createAzureblob`.

- **`files.backends.update` documents more of its 400.** It also answers 400, with the reason, for an updated configuration the server does not admit, such as one that uses ambient host credentials or names a private host.

- **`files.ui.getPage('')`, the root listing, documents its 400 `INVALID_PARAMETER`, 409 and 503.** A query parameter, header or body the operation does not accept is 400 `INVALID_PARAMETER`, and the message names it. With `type` naming a remote backend, the call answers 409 while uploads from before a service restart are still pending on that backend, and 503 when the service cannot connect to it. It also answers 503 `MOUNT_STORAGE_UNAVAILABLE` until the server's storage check passes, and 503 when a journal read could not check its paths in time. The 409, and the 503 for storage and journal checks, send `Retry-After` in seconds.

- **`agent.sessions.delete` documents 409 `session_live` and 503 `session_terminating`.** A hard delete of a session a client is attached to answers 409 `session_live`; one that waited past its bound for the session's teardown answers 503 `session_terminating`. Nothing is deleted in either case, and the 503 is safe to retry.

- **`agent.sessions.create` and `agent.workflows.start` document `session_terminating` more precisely.** The 503 now says the session was shutting down: a concurrent open lost a race with its teardown, and nothing was opened. For `agent.sessions.create`, a retry with the same `Idempotency-Key` while the key's first create is still running answers the same 503; once that create finishes, the retry re-joins its session, or answers 409 `creation_interrupted` if it never started (use a new key then).

- **`exec.schedules.run` documents how `script` is scoped.** An absolute path must be inside scripts-dir. A relative path is scoped like `exec.scripts.read`: on a host that names an execId (`-exec-<id>`) or a subdomain, it is read under that deployment's directory unless it already starts with it. A path outside scripts-dir is 400.

- **The thirty proxy-permission and proxy-hook writes declare `If-Match` as required.** Every write under a container's or a project's proxy permissions — `set`, `delete`, `setDefault`, `enable` and `disable` (the two states of one operation), `deleteAuthGroup`, `setJwtGroup`, `setPasswordGroup`, `setIpGroup`, `setTokenGroup`, `setGroupPermission`, `clearGroupPermissions` and `deleteGroupPermission`, on `api.proxy.containerPermissions` and on `api.proxy.projectPermissions` alike — together with the five container hook writes (`api.proxy.hooks.create`, `set`, `move`, `delete` and `clear`) and `api.proxy.settings.update`, now carries the precondition as a required header. The service has always demanded it: a write that sends no `If-Match` is refused with `428 Precondition Required`, and one whose validator is not a `file:v<N>` strong validator with `412 Precondition Failed`. Only the published contract disagreed, so the SDK and the CLI let such a call go out to fail. `ifMatch` is now a required option, and a call that omits it throws `ValidationError` before a request is sent; the thirty matching commands under `hoody containers proxy …` and `hoody projects proxy …` take `--if-match` as a required option. Read the current `file:v<N>` from the GET beside the write, then write against the version you read.

- **`hoody code extensions list` and `install` no longer take `--id`.** The parameter names the editor instance, and on a `code-N` service URL the platform's edge sets it from the hostname and overwrites whatever a caller sends, so a flag for it described a choice the CLI does not have. The SDK keeps `id` as an optional argument, where it still matters for a client addressed at a bare kit server.

- **`hoody code extensions install` takes `--allow-downgrade` instead of `--as-builtin`.** It permits replacing a staged extension with an older version, and is refused by default so a routine restage cannot silently roll one back.

- **`hoody run <app>` shares its verb with the new subcommands.** An app whose name is also a subcommand of the group — `search`, `resolve`, `config get`, `health`, `resolve`, `test`, `jobs`, `sources`, `profiles`, `recipes` — is read as that SUBCOMMAND, exactly as `hoody agent <container>` already behaves for its own. `hoody run resolve` is the resolver call for such a query, and bare `hoody run` with no app now lists the group instead of reporting a missing argument.

- **Fourteen account commands are accepted only from a first-party login.** `hoody auth claims create`, `hoody auth tokens templates list`, `hoody users onboarding milestones complete`, `hoody users invites redeem`, `hoody users setup retry`, `hoody servers stats`, `hoody wallet github bonus status` / `claim`, and the payment commands `hoody wallet payments stripe checkout create`, `stripe intents list` / `intents get`, `crypto invoices create` and `crypto intents list` / `intents get` reach routes that refuse a delegated credential. Sign in with `hoody login` or `hoody login --web` and they work; called with an API token — `--token`, `HOODY_TOKEN` or `HOODY_API_TOKEN` — the API answers `403 This endpoint requires first-party login (auth tokens are not allowed).` Every other command accepts either credential. Measured against the live API rather than read off the routes: the same token returns 200 on the account, security-history, offer and rental reads beside them.

- **`hoody pipe cheatsheet get` is how the curl cheatsheet is spelled.** The command itself is unchanged; it was published as `hoody pipe examples` in the generated reference, the agent skills and the chat surface, which is a command the CLI has never had.

- **A command's own option is no longer taken over by the CLI's global of the same name.** `hoody agent github auth login --token <pat>` sent no PAT at all: the CLI used to MOVE every recognised global spelling to the front of the command line before parsing it (`hoistGlobalFlags`), so `--token` became the Hoody API token and the GitHub token was dropped, and the account request was authenticated with the PAT. 43 routes were affected, including `hoody browser screenshots capture --format`, `hoody browser pdf export --format`, `hoody files images convert --format` and every command with a `--token`, `--profile` or `--proxy` parameter of its own.

  Nothing is moved any more. Each command carries a HIDDEN copy of every global spelling it does not declare itself, so commander parses the command line exactly as typed and the command's own declaration wins — which is what `enablePositionalOptions()` was always there for. Whichever occurrence is innermost is then merged back into the root options, so `hoody firewall rules list --container <id>`, `hoody config path --config <file>`, `hoody local lock disable --local-password <pw> --non-interactive` and `hoody files version -v` keep working with the flag in any position. Moving tokens had a second cost that is also gone: a removed token is a removed boundary, so the hoist silently changed how the REST of the line parsed (`hoody chat --resume --profile work hello` lost its prompt).

  Where a command owns a spelling, the global stays reachable through its OTHER spellings or before the command: `hoody agent github auth login --token <pat> -t <hoody-token>` sends the PAT in the body and authenticates with the Hoody token. `--container`/`--realm` keep feeding a command's `container_id`/`realm_id` parameter as before, including at root position (`hoody -c <id> proxy create …`).

- **Three parameters that the CLI could not express at all are back.** A parameter whose flag collided with a global used to be dropped from the command entirely: `hoody browser history list --domain`, `hoody notifications list --username` and `hoody notes document get --output` now exist as ordinary local flags. `hoody notes document get` also stops inheriting a configured renderer format as the document format — `output` is no longer bridged from the CLI's configuration into the request, so a configured `table` cannot produce `?output=table` on a route that accepts `json|md|html`.

- **Breaking (CLI): `hoody curl schedules create --request-headers` and `--request-form` take repeatable `KEY=VALUE`.** One entry per flag, as in `--request-headers Accept=application/json --request-headers X-Trace=1`; the value is everything after the first `=`. The JSON object these flags took before is refused with `expected KEY=VALUE`.

- **Breaking (CLI): a flag that takes any JSON value takes an object or an array only from a file.** `hoody curl schedules create` and `update --request-json`, `curl run --json`, `hoody exec store set --value` and `hoody exec scripts returns validate --value` send `true`, `false`, `null` and a number typed inline as that JSON value, and any other inline text as a JSON string, so `--value hello` sends `"hello"`. An object or an array goes in a file, `@file.json`, which is read and parsed and can hold any JSON value, a quoted `"5"` included; an inline value that starts with `{` or `[` is refused. These flags used to send what you typed as a JSON string: an object arrived as a quoted string, and `null` became `"null"`.

- **`hoody agent sessions create --container` is now `--tool-container`.** It is a body field naming the container TOOLS run in, not the container the request is routed to; sharing the spelling with the routing global made a session created against one container claim another.

- **`hoody help <path>` renders the command it names.** `hoody help agent prompt hello --session` printed no help at all (commander read the trailing option as a value and failed); the path is now resolved against the loaded command tree and anything after it is dropped, so that invocation prints `hoody agent prompt`'s help. A top-level alias is resolved before parsing rather than by re-parsing from inside its own action, so the options typed after an alias reach the command it stands for.

- **`--no-color` reaches the client, and `--noColor` means the same thing.** The flag is stored by commander under `color`, which the HTTP client never read; the camelCase spelling meant the opposite of the kebab one once forwarded.

- **`hoody exec` discovers a container's scripts with the routing the user asked for.** Discovery runs before the exec group's own options are parsed, so a `--container` typed after `exec` is read from that option window before the lookup. A flag typed after the SCRIPT name belongs to the script and is left alone: `hoody exec my-script --token <payload>` no longer sends the script's payload as the CLI's credential. A statically generated command such as `hoody exec health` skips discovery altogether. A container or realm typed after the script name still configures discovery — a discovered script cannot own those spellings, since a field named `container` is offered as `--arg-container` — so `hoody exec my-script -c <id>` keeps working. An OWNABLE flag there does not: `hoody exec my-script --token <payload>` is the script's own parameter now, which is the point of the change. A discovered script whose field collides with a process-level switch (`config`, `base_url`, `container`, …) is offered as `--arg-<field>`; the request body keeps the field's real name.

- **The AI auto-fix keeps the rest of the command line.** `hoody filse version --token T --container C` was re-run as plain `hoody files version`, dropping both flags. A corrected command path is now spliced into the original argv; when a suggestion rewrites options that the original line also carries, the suggestion is printed instead of being run.

- **`EventsClient` connects over websocket by default.** `ApiConnecteventstreamWebSocket` now passes `transports: ['websocket']` to socket.io-client unless the caller names a transport. socket.io-client's own default opens with long-polling first and does not fall back to websocket on a failed handshake (unless `tryAllTransports` is set), and a clustered API refuses long-polling with `400`, so the SDK's default events stream could not connect to one at all. An explicit `transports` option still wins; it is only meaningful behind a proxy with `sid` affinity.

- **`daemon.programs.update()` is a partial update.** Its request type is `ProgramUpdate`: every field is optional and an omitted field keeps its stored value, so changing a description no longer means resending `name`, `command` and `user`. Those three stay required on `daemon.programs.create()`, which keeps `ProgramInput`. `hoody daemon programs update` drops the matching required options.

  `sandbox` is the one field on edit with three states. Omitting it keeps the stored block, `sandbox: null` clears it, and an object replaces the block as a unit; the type admits the `null`. On the CLI, `--sandbox null` clears it and the `--sandbox-*` flags set one. Because the block is replaced whole, a CLI edit that sets any `--sandbox-*` flag must resend every restriction it wants kept, and the help of every `--sandbox-*` flag says so; `--port-range-start` and `--port-range-end` carry the same note, since `port_range` is replaced as a unit too. A `webhooks` object requires `enabled` and `urls`, and on edit the daemon replaces those two while keeping `events`, `headers`, `timeout` and `retry` when they are omitted; the `--webhooks-*` help says so, and a partial webhook edit resends `--webhooks-enabled` and `--webhooks-urls`. `webhooks: null` leaves the webhooks unchanged, so the CLI offers no clear flag for it.

  A boolean flag has a `--no-` form wherever the contract tells `false` apart from an omitted value: every boolean on `hoody daemon programs update` (a stored `true` can be set back to `false`), `--no-terminal-interactive` on `programs create` and `ephemeral programs start` (omitted is auto-detection), and `--no-webhooks-enabled` on `create` (the webhooks object requires it). `hoody daemon programs update <id>` with no change flags sends `{}`, the valid empty update, instead of no body; `programs start` and `programs stop` do the same, as their request bodies are declared required. `--sandbox-network-bind-ports null` and `--sandbox-network-connect-ports null` send the field as `null`, not as `["null"]`; a port can never be the string `null`, which is why those two flags take the token while an unrestricted string list such as `hoody watch create --ignore-dirs null` keeps it as a value.

  `daemon.kit.getHealth()` returns `HealthResponse`, the daemon's own envelope with the typed `memory` and `sandbox` blocks; it used to be declared as another kit's health type with an untyped `data`. `daemon.programs.create()`'s response no longer requires `data.id`, which the daemon omits (the id is inside `program`); response fields named `id` are now required only where the schema says so.

  `ready_port` is part of both `ProgramInput` and `ProgramUpdate`, on the CLI as `--ready-port`, and is bounded to 1..65535. `priority` has no declared range on persistent or ephemeral programs; any `u32` is stored as sent. `environment` is typed `Record<string, string>`: the daemon requires string values, and the previous `Record<string, unknown>` let `{ PORT: 8080 }` compile. `stdout_logfile` and `stderr_logfile` must sit under the daemon's log directory, `/hoody/storage/hoody-daemon/logs`, or the request is a 400; omitted, they default to `<name>/stdout.log` and `<name>/stderr.log` under it. The `lines` parameter of the log routes is clamped by the server. `GET /health` carries a `sandbox` object reporting whether `bwrap`, `nft` and `systemd-run` are present, the Landlock ABI level, and the container-wide firewall state. `AddProgramResponse` no longer requires a top-level `id`; the id is inside `program`.

- **Daemon status codes match what the server sends.** An unknown program id is a `400` on edit, remove, enable, disable, start, stop and single status; none of the seven declares a `404` any more. `GET /status` declares no `400`. `POST /programs/{id}/stop` declares no `500`. `POST /programs/{id}/start` declares a `500` only for an `INTERNAL: ` failure, and disable, remove and reset only for a `PERSIST: ` failure. Every body-taking route declares `413` for the 1 MiB request limit, and the ephemeral status and stop routes declare `400` for a malformed id. An id that is not a valid `i32` on any `{id}` route is a plain-text `404` from the path extractor.

- **`--base-url` now outranks every other way of naming the API host.** It was being discarded whenever `HOODY_BASE_URL` or `HOODY_API_URL` was set, or whenever a `baseUrl` had been saved with `hoody config set` — the request went to the saved or environment host instead, without a word. A typed `--base-url` now wins over both, including when it is typed after the subcommand, and `hoody config get --resolved` reports the host the invocation will actually use rather than the saved one. An empty `--base-url` is refused instead of falling back: `--base-url "$VAR"` with an unset variable used to be harmless and would now have outranked the configured host, so it stops the command and says so.

- **A parameter the API requires is now required in the types.** Seventy-nine operations declared a required parameter as optional and then threw at run time when it was missing — the type said the call was fine and only the request failed. The types now match what the service accepts, across files and sqlite (27 operations each), the platform API (8), exec (6), agent and terminal (3 each), run (2), and one each in browser, curl and notifications. **This is a breaking change for TypeScript callers**: code that omitted one of these parameters stopped compiling, in the same place it would previously have failed at run time. The most common is `db` on the sqlite operations. The files count includes the WebDAV verbs, whose required headers are easy to miss.

- **`hoody browser viewport get` and `viewport set` now select the instance with `--browser-id`.** They used to take `--browser-host` and `--browser-port`, which inside a container were accepted and then overridden, so they could not do what their help text implied. Those two flags are gone. `--browser-id <n>` — with `--instance` and `--instance-id` as aliases, as everywhere else in the browser group — sends the command to instance *n*; without it, to instance 1.

- **`hoody files mounts update` can change a mount.** It gains `--vfs-config-*` flags (fields you omit keep their current value), `--auto-deliver` / `--no-auto-deliver` and `--switch wait|immediate`; before, it had no way to say what to change. `updateMount` returns `{remounted, data}`, and `previous_uploads_pending` after `switch=immediate`. A 500 `MOUNT_SWAP_FAILED` means the new settings were saved but not switched in: repeat the update. In this release the server answers an otherwise valid update with 501 and changes nothing.

- **Mount responses use the canonical `vfs_config` field names.** `hoody files mounts create` gains `--vfs-config-read-chunk-size`, `--vfs-config-write-back`, `--vfs-config-poll-interval` and `--vfs-config-read-only`.

- **Breaking: a change to a path that a copy, move, rename or delete is using is refused.** Such a files or WebDAV change, or such an operation on a path in use, answers 409 `FILE_PATH_BUSY` (WebDAV and touch: 423). Two writes to the same file still both run, the last one winning. Every files and WebDAV operation that changes a path can answer 409 `MOUNT_PATH_RESERVED` when the path is reserved for a mount.

- **Mount and backend operations answer 503 `MOUNT_STORAGE_UNAVAILABLE` while the server cannot check its storage.** The answer carries `Retry-After` and comes for an unknown id too; the mount and backend lists still answer. `unmount` and `disconnectBackend` can answer 409 `MOUNT_PATH_CHANGED` (retry) and 500 (the mount is kept; retry later), and a backend's mounts are removed before the backend.

- **Every error body carries `success: false`.** `ErrorResponse` gains an optional `code`, and the 429 limit body declares it too, together with the routes that free a slot.

- **Breaking: `sqlite.kv.exists()` resolves to a boolean.** It returns `true` when the key exists and `false` when the server answers 404 with `X-Hoody-Error-Code` set to `KEY_NOT_FOUND` or `KEY_EXPIRED`. Any other failure still throws an `ApiError`, and so does a 404 without that header, because it comes from an unknown route or a proxy rather than from the key lookup. It used to resolve to the response headers and throw on every 404, so code that caught the 404 to mean "missing" never reaches its `catch` now and treats a missing key as present. Replace the `try`/`catch` with `const present = await client.sqlite.kv.exists(key, { db })`.

- **The request timeout covers the wait for the response headers; the body has an idle timeout.** The SDK and the CLI used to count the timeout across the whole transfer, so downloading a large file, a zip or a pipe's data failed once the timeout passed, even while data was still arriving. Now `timeout` limits the wait for the headers, and a buffered body fails only when no data arrives for that long, with every chunk resetting the clock. Such a body fails with an `ApiError` of code `ETIMEDOUT` whose message says the response body stalled, not that the server never answered. `stream()` and `streamEvents()` are unchanged, and a caller's `AbortSignal` still cancels at any point. In the CLI, screenshot downloads had no limit at all once the headers arrived, and a failed request whose error body stalled could hang; both now use the same idle timeout.

- **An error's code is read from the `X-Hoody-Error-Code` response header when the body has none.** A HEAD answer has no body, so a kit that names the reason for a HEAD failure puts it in that header. The SDK and the CLI now set `ApiError.code` from it, so `hoody kv exists` on a missing key reports `KEY_NOT_FOUND`. A code in the body still takes precedence, and a header value that is not an upper-case code is ignored.

- **Breaking: `notes.files.download()` takes `(notebookId, fileId)`.** The arguments were in the opposite order from every other notes file method. Both are strings, so a call written for the old order still compiles and now asks for the wrong file: swap the two arguments.

- **Breaking: boolean query parameters are typed `boolean`.** Flags such as `include_proxy_domains` on `api.containers.list()` and `get()`, and `errors_only` on `api.activity.list()`, take `true` rather than the string `'true'`. On the CLI, an optional boolean filter can still ask for `false`. A command without positional arguments takes `--flag [true|false]`, where a bare `--flag` means `true` and any other value is a usage error: `hoody proxy aliases list --enabled false`. A command with positional arguments takes `--flag` or `--no-flag`: `hoody containers get <id> --no-include-proxy-domains`; a `true` or `false` written after such a switch is refused.

- **Breaking for TypeScript: the login response type names its three outcomes.** `api.auth.login()` resolves with tokens, a two-factor challenge (`requires_2fa`, `temp_token`) or an `auth_intent_token`. Narrow before reading the token: `if (data && 'token' in data) hoody.setToken(data.token)`. On user responses, `email`, `public_key`, `metadata`, `onboarding`, `created_at` and `updated_at` can be `null`.

- **`adoptSession()` takes a login response as it comes.** Pass it the result of `api.auth.login()` without narrowing. A two-factor challenge or an `auth_intent_token` throws a `ValidationError` naming the call that finishes the login (`completeTwoFactorLogin()`, or `api.auth.oauth.authorize()` and `exchange()`).

- **`setToken()` changes one client.** It sets the token of the client it is called on, which leaves the session it shared with the clients derived from it or its parent. Use `setSessionToken()` to change the whole session.

- **A client addressed at the account API refuses Kit calls until you `withContainer()`.** They used to go to the API host. The client treats `baseURL` as the account API when it is a Hoody API host, when you pass `credentials`, or when you pass no `baseURL`; any other host is used as given. Set `target: 'account'` or `target: 'kit'` to say which when the host does not tell.

- **Realm routing.** A call can pick its realm with `_realm`, a realm id or `null` for none. A generated call on a realm-scoped client goes to the realm host when a middleware moves it anywhere inside the API; a destination outside the API is left to the middleware. A realm-scope 403 is an `ApiError` with `code: 'REALM_SCOPE_ERROR'` (test it with `isRealmScopeError()`) and no longer costs a second request to list the allowed realms, unless you set `realmErrorIntrospection: true`. The SDK's login, two-factor and token-refresh calls refuse HTTP redirects.

- **GET responses are not cached unless you turn it on.** The cache used to be on by default. Enable it with `cache: { enabled: true, ttl }` on the client, or with `cache: true` or a TTL on one call.

- **`ApiError.code` is read from more places.** In order: the body's `code`, a code-shaped `error` string, a nested `error.code`, then the `X-Hoody-Error-Code` header. A lower-case `error` message is not a code.

- **A method's declared body type holds whatever `Content-Type` arrives.** Eleven methods that return bytes, such as `files.archives.readMember()`, `files.zip()` and `browser.page.exportPdf()`, read the body as an `ArrayBuffer`, and seventeen that return text read a string. A `responseType` you pass still wins.

- **`listAll()` and `listIterator()` follow the pagination the operation uses.** They walk by page, offset or cursor and start where your arguments say (a numeric cursor included). An operation that declares pagination but takes no page, offset or cursor parameter gets a `listAll()` that is one request, and throws when that response holds fewer rows than its own total; a list that declares no pagination, such as `daemon.programs.list()`, has no `listAll()` or `listIterator()`. A walk that stops advancing (the same rows twice, or the 1000-page cap) throws rather than returning a partial list, and so does a cursor walk whose cursor ends while `total` says rows remain; a page or offset walk ends on an empty page. A page walk that starts past page 1 counts the rows before it at the page size the server reports, or, when it reports none, at the length of the first page it served, and never takes a short page as the last one. A server that clamps the limit is walked to the end; without a reported size, a short last page costs one more request, which comes back empty. `watch.events.listAll()` and `listIterator()` walk by `after_id`, so rows written during the walk are neither skipped nor repeated.

- **The API answers 400 for a malformed `filter`.** A `filter` that is not a JSON object is refused, and so is one that names an unknown column or operator on `api.wallet.listTransactions()` or `api.wallet.listInvoices()`.

- **sqlite classifies a failure of your own SQL.** On query, transaction items and `COMMIT`: `400 SQL_ERROR`, `400 SQL_BIND_ERROR`, `409 SQL_CONSTRAINT`, `409 DATABASE_READONLY`, each with SQLite's message, and `503 DATABASE_BUSY` and `503 REQUEST_TIMEOUT`, with a generic message (a 5xx body never carries SQLite's text). Anything else is `500 DATABASE_ERROR` with a sanitised message. A `noFail` item carries the same `code`. A directory-mode KV store's `.hoody_sqlite/cache.db` can be neither created nor deleted as a database (`400 INVALID_DB_PATH`), whether by `POST /db/create` or by `create_db_if_missing` on `POST /db` and the KV writes, and neither can its `cache.db-wal`, `-shm` and `-journal` files.

- **watch refuses a body it cannot read with `400 INVALID_REQUEST`.** A `createWatcher` or `updateWatcher` body that is not JSON, arrives with the wrong content type, has a field of the wrong type or is too large answers `400 INVALID_REQUEST` with `{ code, message }`; it used to be a `text/plain` 400, 415 or 422. An `updateWatcher` body that names an unknown field is refused the same way. An `updateWatcher` with no field answers `400 INVALID_REQUEST` ("nothing to update"), and one whose fields all equal the current values returns the watcher without restarting it.

- **curl: an id that is not a UUID is a 404.** `getJob`, `getJobResult`, `getSchedule` and `deleteSchedule` no longer list a 400. Idle cookie sessions are deleted after 720 hours (30 days) without use, the kit's `--session-idle-retention-hours` default; the same session id then starts an empty jar.

- **Download and extraction lists show only the jobs you may read.** `GET /api/v1/downloads` and `/api/v1/extractions`, and WebDAV `?downloads`, `?extractions`, `?download_history` and `?extraction_history`, list a job only when the caller may read its paths. Unless the caller has read-write access to `/`, a listed URL loses its user, password, query and fragment, in `url` and in `error_message`. A deployment without auth rules lists what it did before.

- **The API refuses a `page` or `limit` that is not a whole number.** `limit=2.5` answers 400 where it answered 500, and `page=abc` or `limit=abc` is refused rather than silently replaced by the default. An empty `page` or `limit` (`limit=`) and a page above the maximum are refused with 400 too; `limit=` no longer returns every row. Several lists now declare both parameters as integers.

- **The tunnel's 400 for an upgrade with no supported subprotocol is `text/plain`.** The response carries `Content-Type: text/plain; charset=utf-8`.

- **Files path routes name their refusals.** Refusals carry a `code`: `ACCESS_FORBIDDEN`, `RESOURCE_NOT_FOUND`, `INVALID_PATH`, `PATH_CONFLICT`, `OVERWRITE_REFUSED`, `DIRECTORY_EXISTS`, `PAYLOAD_TOO_LARGE`, `UPLOAD_INCOMPLETE`, `REMOTE_UPLOAD_FAILED` and `MOUNT_PATH_RESERVED`. `INVALID_PARAMETER` now means only that the request itself is wrong; a failure a changed request would not fix carries no code. `files.archives.extractMember()` can answer 409 when the extraction was cancelled or its path is busy or reserved. Cancelling a URL download removes the partial file only on a local filesystem where the file's inode proves it is the download's; on FUSE, NFS, CIFS and overlayfs the partial file is kept.

- **`EventsManager` delivers events only after the server's `welcome`.** Frames that arrive earlier are buffered, not dropped. A server that sends no `welcome` fails the connection after 10 s (`welcomeTimeoutMs`). The legacy `onX` helpers keep working on top of the new runtime.

- **Subscribing to a project or container room no longer selects which events arrive.** The server sends each connection every event its credential may read, whatever rooms it joined. A `subscribe` frame carrying `projectId` or `containerId` is still accepted for compatibility and changes nothing. Narrow on the client with `filter: { projectId, containerId }` on `on()`, `waitFor()` or `stream()`.

- **Cursor-mode event history reports `total: -1` and `offset: 0`.** `GET /api/v1/events` with `after` or `bootstrap=true` pages by cursor, adds `next_cursor` and `latest_cursor` to `pagination`, and does not count rows. Offset paging, the default, is unchanged. It never returns global events (broadcast notifications, `server.offer.*`); those come through the stream and cursor history.

- **Every kit `open` command builds its URL with the SDK's embeds builder.** `hoody <kit> open` and `hoody open <kit>` print or open the URL `client.embeds` builds and refuse what it refuses. A kit with several views takes `--view`, and each typed view parameter is a flag, except the terminal and agent `theme`, an object that only the SDK sets. `--url` prints the URL and nothing else: it no longer starts the browser instance. `hoody desktop open [n]` opens the desktop kit's own `desktop-<n>` URL. `hoody code embed <PUBLISHER.NAME>` keeps `--folder` optional (without it the edge supplies the default workspace) and refuses what `hoody code open --view extension` refuses: an index outside the bounds, and a folder or locale that does not match the published pattern.

### Removed

- **Breaking: eleven `files.backends` connect methods are gone.** `connectAlias`, `connectCache`, `connectChunker`, `connectCombine`, `connectCompress`, `connectCrypt`, `connectHasher`, `connectLocal`, `connectMemory`, `connectTardigrade` and `connectUnion` are no longer operations of the files service, so the SDK methods, their request types and their reference pages are removed.

- **Breaking: `files.backends.connectStorj` and `connectUptobox` are gone.** Storj is unavailable in this release of the files service (its setup could hold up every other backend's connect), and rclone v1.75.1 has no Uptobox backend. A saved Storj backend is kept but not connected.

- **The four daemon page-collecting helpers are gone (named as they were in beta.14): `daemon.programs.listAll`, `daemon.programs.listIterator`, `daemon.quickStart.listAll` and `daemon.quickStart.listIterator`.** Neither route paginates, and the helpers read their items from a `data.items` field that neither response carries, so all four reported an empty inventory for a container full of programs. The spec no longer claims those two listings are paginated, so the SDK no longer emits a collector for them. `daemon.programs.list()` returns every program in `data.programs`, and `daemon.ephemeralPrograms.list()` returns every entry in `data.ephemeral_programs`; both were always whole-collection reads.

- **Nine `hoody code` commands are gone, and none of them could ever have worked.** `code auth mint-key`, `code auth login`, `code auth submit`, `code auth logout`, `code proxy`, `code proxy-path`, `code check-update`, `code assets static` and `code assets injected-script` addressed routes the Code kit's orchestrator does not serve. Every one of these commands reached a service with no handler for it. The `code auth` group goes with them. **This is a breaking change** for anyone scripting against those commands, and there is no replacement, because there was never a working call.

  `code check-update` is the one with a successor. `hoody code version` reports the orchestrator and the packaged editor as two independent versions; it is not a renamed update check, because the editor is vendored and pinned in-repo, so there is no release feed to compare against and no `latest` to report.

- **The spec- and docs-serving operations are no longer SDK methods.** Eighteen operations across nine kits whose only job was to serve an OpenAPI document or a Swagger/Redoc UI — `agent.system.docs`, `agent.system.openapiJSON`, `agent.system.openapiYAML`, `browser.health.getOpenApiJson`, `browser.health.getOpenApiYaml`, `code.static.getOpenAPI`, `cron.system.getOpenApiJson`, `cron.system.getOpenApiYaml`, `exec.system.getOpenApiJson`, `exec.system.getOpenApiYaml`, `run.documentation.getOpenApiJson`, `run.documentation.getOpenApiYaml`, `sqlite.docs.getJson`, `sqlite.docs.getYaml`, `terminal.docs.getJson`, `terminal.docs.getYaml`, `watch.system.getOpenApiJson` and `watch.system.getOpenApiYaml` — are gone from the client. They returned a spec file or an HTML app shell, neither of which a typed client can do anything with, and the routes themselves are unchanged: request them directly if you need the document a running kit serves.

- **Breaking: `patchFileApi` loses its `backend` parameter.** The server refuses it with 400 `INVALID_PARAMETER`, so the SDK option and its CLI flag are gone. Use the file read, write, delete and mkdir operations for remote backends. `files.backends.createMailru` loses the `quirks` option, and the `cache` backend's `chunk_path` and `db_path` lose their published default.

- **Operations the specs keep off the SDK are no longer SDK methods.** `api.authentication.githubOAuthRedirect`, `githubOAuthCallback`, `googleOAuthRedirect`, `googleOAuthCallback`, `oauthDeviceAuthorize` and `oauthLaunchStart` (browser redirects and pages), `api.meta.getSocialStats`, `api.waitlist.waitlistJoin` and `waitlistEnrich` (website endpoints), and `run.run.healthCheck`, `runPathBased` and `runTerminalAnchored` (launch paths) are gone from the client. The routes are unchanged, and `hoody meta config get`, `values get`, `social stats`, `hoody auth waitlist join` and `update`, `hoody run health` and `resolve` remain CLI commands.

- **`files.git` is gone.** Its one method, `fetch()`, and `hoody files fetch-from-git` addressed a Git read that no files backend implements.

- **`tunnel.tunnelConnect()` is gone.** A plain HTTP request cannot upgrade to the tunnel's WebSocket. Use the package-root `tunnelConnect`, `tunnelExpose`, `tunnelPull` and `tunnelServe`.

- **Page-collecting helpers on listings that do not page are gone.** `api.firewall.listAll` and `listIterator`, `terminal.sessions.listAll`, `listIterator`, `listHistoryAll` and `listHistoryIterator`, and `terminal.system.listPortsAll`, `listPortsIterator`, `listProcessesAll` and `listProcessesIterator`. Each route returns its whole list in one response, so `api.firewall.listRules()`, `terminal.sessions.list()`, `terminal.commands.list()`, `terminal.system.listPorts()` and `terminal.processes.list()` already return every item. The removed helpers are named as they were in beta.14.

### Fixed

- **`hoody pipe send` / `receive` no longer hang after an error while a command's output is unread.** Under Bun the CLI forwards a `--from-cmd` / `--to-cmd` command's output to a FIFO or socket stdout/stderr; after an error it waited for that forward with no limit, and an early `send` error stacked two 10 s waits. One 10 s deadline now covers the command's output and the CLI's last lines, then the CLI exits 1.
- **`hoody pipe` keeps its last error lines on a slow stderr under Bun.** When a `--from-cmd` / `--to-cmd` command filled the CLI's stderr (a named FIFO or socket read slowly) and failed, the CLI's own `Error:` line could be lost at exit. The same could happen to the long error of `health` and `help`, and to the last lines of a failed `progress` watch. The CLI now waits for those lines before it exits, for at most 10 seconds; the exit code is unchanged.

- **`hoody pipe` commands use the CLI's proxy, and every CLI command honours `NO_PROXY`.** The pipe commands' HTTP requests (send, receive, status, progress, health, metrics, `forward` over HTTP) ignored the proxy set with `--proxy`, the `proxy` config setting or `ALL_PROXY` / `HTTPS_PROXY` / `HTTP_PROXY`. They now go through it like the CLI's other requests. Under Bun (the standalone `hoody` binary), `--proxy` and a config-file proxy now apply to every CLI request; before, only an environment proxy did. Hosts listed in `NO_PROXY` / `no_proxy` (exact names, `.domain` or `*.domain`, `*`, optional `:port`, comma- or space-separated) are reached directly under both runtimes. An invalid proxy URL is no longer echoed in the warning or the `--debug` output, so a password in it is not shown. WebSocket connections (`pipe connect`, `forward --ws`) are not proxied.
- **`PipeWsError.status` on a refused pipe `connect()` without kit credentials.** Under Node.js and Bun with no `kitAuth`, the socket came from the runtime's WebSocket, which hides the HTTP status, so `.status` was `undefined` (under Bun it was missing with credentials too). Outside a browser `connect()` now always opens through the `ws` package and reads the status (Bun: from its `unexpected-response` event); in a browser it stays `undefined`.
- **Tunnel responses stream, at any size.** `expose()` (and so `hoody tunnel expose` and `hoody share`) read the whole local response before sending any of it, and refused one over 64 MiB: the public URL answered 502. A file over 64 MiB shared with `hoody share` could not be read in the container, not even its first megabyte, and every smaller response arrived only once the local service had sent all of it.
  - The head goes out as soon as the local service sends it, and the body follows as it is read, under the tunnel's flow control. At most 1 MiB is read ahead of what the tunnel has taken, so a slow reader slows the local service instead of filling memory.
  - A local response that ends early, after its head was sent, ends the stream with a reset, never as a complete short body.
  - A response to a HEAD request, a 204 or a 304 is complete at its headers even when it carries a Content-Length. One used to wait for a body that never comes.
  - A visitor that cancels a request ends the local request at once and closes its connection. A response delimited by the connection's close is not taken as complete, and no end-of-stream follows the visitor's reset.
  - Each request ends with one terminal frame, and never answers the visitor's reset with one of its own. A reset reaches the kit even when the tunnel connection that carried the stream is closing.
  - A WebSocket (upgrade) request whose visitor leaves before the local service answers closes its local connection at once. A local service that resets the connection after switching protocols ends the stream with a reset; nothing used to be sent, and the stream stayed open.
  - A visitor's reset closes an upgraded or TCP stream's local connection, even when the local service keeps its side open. A TCP visitor that half-closes after its request gets the whole answer and then its end; the end never came, and a half-close before the local connection was up dropped the request. When the tunnel connection drops or the session is closed, every request it was serving ends its local request. A reconnected tunnel used to find every pooled local connection still taken, and failed with "local connect failed".
  - A request still in flight when the tunnel reconnects to a fresh session ends without touching that session's streams, which start again from the same IDs: its late end or reset used to close, or unregister, the new stream that took its ID. A visitor's reset also cancels a TCP stream's local connection while it is still connecting.
  - A WebSocket (upgrade) or TCP stream whose local service sends and closes while the tunnel is short of credit delivers every byte before its end: the bytes that came with the 101 could be dropped behind the end-of-stream, and a read over 64 KiB ended a TCP stream. Credit for data received before a reconnect is no longer sent on the new connection, where it made the tunnel close the session.
  - A WebSocket (upgrade) stream whose local service resets its connection ends with a reset at once, even while data waits for the visitor to take it; it used to wait for that data, which could hold the tunnel's shared credit for good. A 101 whose first frames arrive in the same read as its headers is no longer refused as headers too large.
  - A TCP stream whose local service ends cleanly while its last bytes wait for the visitor, and which the visitor then cancels, sends nothing more: an end-of-stream used to follow the cancellation.
  - A request whose stream ends while its data waits for the tunnel's shared credit gives up its place at once. It used to hold it until the tunnel next granted credit, and requests behind it waited longer.

- **CLI downloads are byte-exact.** The CLI read every response body that was not JSON as text, so an image, a PDF, an archive or a binary file came out with each invalid UTF-8 sequence replaced, and exited 0; `-o raw` removed the JSON quoting but not the decoding. The 30 commands that can answer with a file now write it as received: 14 whose answer is always bytes (`browser pdf export`, `curl storage get`, `files uploads download`, `files archives members read`, `files zip`, `files images convert`, `files ssh get`, `images icon get`, `notifications icons get`, `terminal sessions read`, `terminal sessions screenshots capture`, `wallet invoices download`, `notes files download`, `notes document blocks export`), and 16 where the response's Content-Type decides (`browser screenshots capture`, the six `display screenshots` and `display thumbnails` commands, `files get`, `kv get`, `curl run`, `curl jobs result get`, `notes avatars download`, `files archives preview`, `files ftp get`, `files s3 get`, `files webdav get`). A JSON or text answer to one of the 16 prints as before.
  - `--out-file <path>` saves the body byte for byte whatever its type, text and JSON included. It writes a temporary file in the same directory and renames it over the target, so a failed transfer leaves an existing file as it was. `--out-file -` writes the body to stdout.
  - Bytes go to stdout with nothing added. When stdout is a terminal and the first 4096 bytes hold a NUL byte, the command refuses and names `--out-file`; `--out-file -` prints anyway.
  - `-o json` and `-o yaml` cannot print bytes: with `--out-file <path>` they print `{ saved_to, bytes, content_type }`, and without it the command exits 1.
  - A transfer that stalls for the request timeout, or ends short of its Content-Length, exits 1. So does an output that fails (a full disk), at once, with the output's own error. A reader that closes the pipe (`| head -c 100`) ends the command with exit 0.
  - When the file is saved but the `-o json` or `-o yaml` summary cannot be written for any reason other than a closed pipe, the command keeps the file, says so on stderr and exits 1.

- **`exec.scripts.list({ exhaustive: true })` lists.** The SDK added its default list filters (`filter`, `metadata`, `label` and the rest) to every listing, and the exec kit refuses an exhaustive listing with any option that could hide an entry, so every exhaustive listing failed with a 400. An exhaustive listing now sends only the options you pass.

- **The SDK source type-checks under `verbatimModuleSyntax`.** `generated/client.ts` imported the type `IHttpClientConfig`, and `lib/terminal-client.ts` the type `DuplexOptions`, as values, so a project compiling `hoody-sdk`'s TypeScript with `verbatimModuleSyntax` got `TS1484`. Both are type imports now. The emitted JavaScript is unchanged.

- **A request without a body carries no `Content-Type`.** The SDK, in Node and in the browser, and the CLI sent `Content-Type: application/json` on every request, so a DELETE or POST with no body reached the kit as an empty JSON request, and a kit that reads the body by its type refused it: `notes.notebooks.delete()` and `hoody notes notebooks delete` / `notes nodes delete` answered 400 "Body cannot be empty when content-type is set to 'application/json'". A request with no body now goes out with no `Content-Type`, including one set in `headers`, since there is no body for it to describe; event streams already worked this way. A request with a body keeps its type: `application/json` by default, or the one the caller set.

- **The SDK source type-checks under `@types/bun`.** A project that compiles `hoody-sdk`'s TypeScript with Bun's types and `exactOptionalPropertyTypes` got an error in the event-stream read loop (`TS2322` on TypeScript 7, `TS2375` on 5): the loop declared the DOM read-result type, and Bun declares the end of a stream without a `value`. The loop now takes its type from the reader, so it compiles under either set of types. Nothing changes at run time.

- **Desktop notifications from `NotificationDisplayClient` keep their urgency and timeout.** The notifications kit sends `urgency` upper-cased (`LOW`, `NORMAL`, `CRITICAL`) and the expiry as `timeout`; the presenter read only lower-case urgency and an `expire_time` field, so every notification showed at normal urgency (no sound, no `requireInteraction` in the browser for a critical one) and with the system's default expiry. Both are read now, and a lower-case urgency still works. `ParsedNotification.data` is typed from the kit's `Notification`, with every field except `id` optional. Code that reads or builds `ParsedNotification.data` itself sees two changes: `urgency` is the kit's upper-case value (`'LOW' | 'NORMAL' | 'CRITICAL'`, normalised from any case), and the expiry is `timeout` (milliseconds; `-1` = the notification server's default, `0` = never expires, passed to notify-send as `--expire-time 0`) instead of `expire_time`. In the browser, an empty `summary` or `body` now falls back to `appname` / `message` as it already did under Node.

- **`notifications.listIterator()` / `listAll()` follow the kit's cursor.** The listing pages forward by `cursor`, but the spec declared it in the offset slot, so the helpers sent a row count as `cursor`. They now send each page's `next_cursor` back as `cursor` while `has_more` is true.

- **Signing in with an email address works.** The API accepts either a username or an email, but the SDK and the CLI only ever sent what they were given as a username — so an account addressed by its email was rejected before the request reached the server. `authenticate()` and `login()` now accept either form, and the CLI sends whichever one you typed. The two are not interchangeable at the API, so an email offered as a username (or the reverse) was refused rather than silently retried; this is why a stored email address could not sign in at all.

- **Mount size and duration flags accept strings such as `10G` and `5m`.** `--vfs-config-cache-max-size`, `--vfs-config-cache-max-age` and `--vfs-config-dir-cache-time` on `hoody files mounts create` were typed as numbers, so a unit such as `G` or `m` was refused; exec flags that take a number or a string, such as a timeout of `5m` or `unlimited`, had the same fault.

- **`agent.hooks.list({ session_id })` and `agent.todos.list(…)` work.** Both are GET routes whose spec also declares a request body, and the SDK put those fields in a body, so the browser's `fetch` refused the call ("GET/HEAD method cannot have body") before it was sent. A GET or HEAD operation now sends those fields as query parameters; when the same name is also passed as a query option, the query option wins.

- **Box clients in the browser no longer warn about transport options you never set.** `withContainer()` and `withRealm()` copied the parent client's transport settings with every default filled in, so each derived browser client logged "ignores Node-only transport options: connections, pipelining, …". Derived clients now receive only the transport options the caller passed, available as `http.getConfiguredTransport()`.

- **Credentials follow where a URL goes, not how it is spelled.** Every credential check (the API bearer, the body of the SDK's own login, two-factor and refresh calls, realm routing and kit credentials) resolves the URL as the transport's `fetch` does, against the page in a browser. A request middleware that rewrote a request to `HTTPS://elsewhere`, `//elsewhere` or a backslash spelling of it kept the API bearer, and on a client without a `baseURL` a login rewritten that way was sent.

- **A kit credential under a header name you chose is treated as one.** With `kitAuth: { type: 'token', header: 'X-Access-Pass', value }` (or `jwt` with `header`), the header no longer follows a middleware to another origin, and `ApiError.request.headers` shows it as `[REDACTED]`.

- **A relative `baseURL` applies a realm, or refuses it.** A client created with a relative base such as `/proxy` is an account client: in a browser the base is resolved against the page, so `withRealm(id)` and `_realm` go to the realm host of the page, and where it cannot be resolved (Node) a request that asks for a realm is refused with a `ValidationError`. It was read as a kit URL, so `withRealm(id).http.get(…)` sent the bearer to the account API without the realm.

- **A raw `.http` request with a realm is refused, not sent unscoped, on a client that treats its base as a kit.** A base that is not a Hoody API host, such as `https://app.example.com/proxy`, is used as a kit or daemon reached directly. The generated services applied a realm there, but `client.http` had no realm host: `withRealm(id).http` sent the bearer to that base without the realm, while the relative spelling `/proxy` applied it. A raw request bound for that base host now throws a `ValidationError` that says to drop the realm or pass `target: 'account'`, and with `target: 'account'` the realm is applied as it is for `/proxy`. A base host that already carries the realm (`https://{realmId}.api.example.com` with the same `realmId`) is sent as before, and a trailing-dot spelling of the base host (`host.`, `host%2e`) counts as the base host. The generated services are unchanged.

- **A browser client without a `baseURL` applies a realm.** It takes the page's origin as its base, so `withRealm(id)` and `_realm: id` go to `{id}.<page host>`; they went to the page's own host, unscoped. `client.http.getBaseURL()` returns that origin. A realm that cannot be applied, on a host of fewer than three labels or with no base URL and no page, is refused with a `ValidationError` instead of being sent without it.

- **A command that asks for confirmation fails when nobody answers.** When stdin closes before an answer, as in a script, a pipe or `< /dev/null`, or no answer comes within 30 seconds, the command exits 1 saying the action needs confirmation and to pass `-y`, and sends nothing. It used to take either as No, print "Action cancelled" (or "Confirmation timed out — defaulting to No.") and exit 0, so a script that forgot `-y` did nothing and reported success. An explicit `n` still cancels with exit 0.

- **Commands whose request body is optional no longer demand `--body '{}'`.** Sixteen `hoody agent` commands, among them `github repos credentials set`, `stash push` and `stash pop`, `todos start`, `todos triage` and `todos archived purge`, `agent memory flush`, and `loops runs start` and `loops delete`, send `{}` when `--body` is not given. `--body` still sends what you write, which `agent hooks reload` needs for its `session_id`.

- **`hoody curl jobs cancel` reports what the server did.** It says whether the job was cancelled or deleted, whether it was purged and how many files were removed; it used to print "Deleted successfully." whatever happened.

- **daemon: streaming a program's log cannot reach a file outside the log directory.** The log file is opened beneath the log directory with containment the kernel enforces, which closes a race in which a symlink swapped in after the path was checked streamed a file outside it. A log path that is not a regular file is refused.

- **sqlite: a database that cannot be opened is a server error.** A database that passes path validation but fails to open, with corrupt pages or an I/O error, answers `500 DATABASE_ERROR` with a sanitised message; it answered 400 with SQLite's text. Contention, a deadline or a shutdown during the open answer `503 DATABASE_BUSY`, `503 REQUEST_TIMEOUT` or `503 SERVICE_UNAVAILABLE`.

- **sqlite: `POST /maintenance` with `vacuum_into` cannot write a KV store's cache.** A destination that is a store's `.hoody_sqlite/cache.db`, or its `-wal`, `-shm` or `-journal` file, answers `400 INVALID_DB_PATH`, including through a symlinked path.

- **notes: an unknown or expired socket id closes the WebSocket with code 1008.** The close reason is "Socket ID is invalid". The server used to attempt the invalid close code 401, and the connection dropped with 1006 instead.

### Security

- **A request that carries a credential never follows a redirect blindly.** The SDK, in Node and in the browser, and the CLI follow a redirect of a credentialed request only while it stays at the destination the request was addressed to (the API and its realm hosts, or one kit origin), for at most 5 hops, all within the request's one timeout. Any other redirect is refused with an `ApiError` whose `code` is `REDIRECT_REFUSED`, and nothing is sent there. fetch strips only `Authorization`, `Cookie` and `Proxy-Authorization` when it follows a redirect to another origin, so a kit credential under any other header name (`X-Hoody-Token`, the container claim, a `kitAuth` header you named, the CLI's `--kit-token-header`) or in the query string reached whatever origin the redirect named. In a browser, which does not reveal where a redirect leads, every redirect of a credentialed request is refused. `hoody proxy logs` and the one-shot `hoody shell <id> -- <command>` sent the kit credential through the runtime's own fetch; they now go through the CLI's transport, so this rule applies to them, and so do the CLI's proxy settings. A 307 or 308 resends the method and body; a 303, and a 301 or 302 of a POST, continue as a GET without a body. `probeKit()` no longer follows redirects, and neither does a pipe helper built from a bare URL when its request carries a credential header, the container claim or a token in the URL. A request without credentials follows redirects as before.

### Known issues

- **`files.backends.createS3()` lists example endpoints as an enum.** The `endpoint` option is optional, but its type and `hoody files backends s3 create --endpoint` still offer rclone's example endpoints as the allowed values. Any S3 endpoint works; the list is examples only.

Two PULL bindings on different `127.0.0.0/8` addresses can legitimately hold the same port at the same time, so without it the rows were distinguishable only by bind id and gave no way to reach either socket. An EXPOSE binding takes `0.0.0.0` and omits the field.

### Changed

- **`agent.tasks.listTasks()` returns the task list instead of asking for one.** The call used to ask a live session to emit its background-task snapshot and hand back an empty acknowledgement, with the snapshot arriving separately on that session's WebSocket or SSE stream. It now answers inline with `items`, `meta` and `session_live`. Nothing has to be attached and no session has to be live, so the `503` that reported a busy daemon or an exhausted stream-concurrency budget is gone from this endpoint.

  The list is the union of the live task registry and the persisted per-session store, keyed by task id, with the live entry winning where both hold one. The registry evicts a completed task when the next one spawns, so a task can leave memory while its transcript is still on disk; reading only the live side would hide it. `session_live` reports whether a live session backed the read.

- **`agent.tasks.requestTaskTranscript()` is now `agent.tasks.getTaskTranscript()`, and it returns the transcript.** The CLI command moves with it: `hoody agent tasks request-transcript` becomes `hoody agent tasks transcript`. The old call was an acknowledgement whose transcript arrived on the session's stream. The new one answers inline with the entries, the task's own record, and the cursor state.

  Neither an attach nor a live session is needed. A task that reached a terminal state is persisted per session, so its transcript reads back for a dormant session and across a daemon restart. A task still running when the daemon died is not recoverable, because persistence happens at terminal status, and it answers `404`. `source` is `live` or `store` depending on which side served the read. `complete` reports whether the response reflects a terminal projection that is durably committed to the store, so it is false for a task that has just finished but whose write has not landed, and false for a placeholder written by session teardown whose real projection may still arrive.

  `after_seq` is an exclusive upsert-poll cursor: entries whose sequence is strictly greater than it, plus any entry still open regardless of its sequence, since viewers upsert by sequence. Omitting it returns the whole transcript, which is not the same as passing `0` — that value is exclusive and skips a closed entry at sequence 0. It is not the `after_turn` cursor that `getSessionTranscript()` takes, not the gateway's stream sequence, and not a monotonic replay cursor.

### Fixed

- **Stopping a local exit no longer clears an upstream that belongs to a different one.** When a local exit loses its session, the SDK clears the container's upstream and confirms by reading it back. Calling `stop()` on that same handle afterwards used to read the upstream again and delete it if it looked like the one this handle had written, and that comparison cannot tell two exits apart: the kit reports `auth` as a bare boolean and never any credential identity, so a second exit that had since bound the same loopback port produced an identical status object and had its upstream deleted.

  A handle that has already confirmed its own upstream is gone now issues no further delete, whatever it reads. It still closes its tunnel and removes its proxy alias. This only ever affected a stale handle, since two live exits cannot collide on a loopback port at all: the bind is a real listener, and an occupied port fails rather than being shared. Closing the rest of the gap needs an atomic compare-and-delete in the kit, because every discriminator the SDK writes comes back collapsed to `auth: true`.

## [1.0.0-beta.13] — 2026-08-11

### Added

- **Publish a container's HTTPS proxy and exit from your own machine.** `hoody egress local <container>` turns the container's egress URL into an ordinary HTTPS proxy whose exit IP is the machine running the command. A request arrives at `https://<project>-<container>-egress.<server>.containers.hoody.com`, the container's egress proxy chains it to a SOCKS5 port on container loopback, that port is a tunnel-kit bind, and the CLI terminates SOCKS5 and dials the destination locally. Nothing listens on your machine: the only local sockets are outbound, one WebSocket to the kit and one TCP connection per proxied request.

  Destinations are authorized before the dial rather than after. The command resolves the hostname, checks every address the lookup returned, and connects to the address it approved, so a public name with a private A record cannot reach your LAN and a second lookup cannot swap the target after approval. Ports 80 and 443 are allowed by default; `--allow-ports` widens that and takes `*` for any port. Private, loopback, link-local and reserved addresses are refused unless you pass `--allow-private`, which turns off all of those checks at once, including the one covering `169.254.169.254`. Once the chain is wired the exit IP is confirmed through `ip.hoody.com`, which `--no-verify` skips.

  The container URL is the credential here as everywhere else, so anyone holding it can relay traffic through your connection. Set proxy permissions before sharing it. `--alias <name>` and `--auto-alias` publish it behind a proxy alias so the URL carries no container ID.

  The SDK exposes the whole command as `startLocalExit()`, and the layers under it separately, because each is usable on its own: `tunnelSocks5()` binds a SOCKS5 port over a tunnel session, `handleSocks5Stream()` runs RFC 1928 over any stream you hand it, and `resolveAndAuthorizeDestination()` is the destination gate. CONNECT is the only SOCKS5 command implemented. BIND, UDP ASSOCIATE and IPv6 destinations are refused.

- **`hoody egress` reads and sets the container's upstream proxy.** `egress health` reports the service. `egress upstream get` shows the upstream a container currently chains through, `egress upstream set <url>` routes it through one, and `egress upstream clear` sends it out direct again.

- **Poll for new notifications without downloading any.** `api.notifications.getUserNotificationSummary()` returns the unread count and the position of the newest notification and nothing else, so a client can check for activity cheaply and fetch the list only once something has moved. An auth token needs `resources.read_account` to call it and gets a 403 without, the same as the list endpoint, because a count and a newest-timestamp on their own still report when an account is active.

### Fixed

- **A `.` or `..` in a path handed to the files, pipe or exec helpers no longer redirects the request.** These helpers interpolate your path into a route, and the separators have to survive that, so a relative segment was resolved by the URL parser before the request was ever sent. Against the files helpers a path beginning `../../` climbed out of `/api/v1/files/` and landed on an unrelated route, and it went out with your token attached. The kit rejects those segments itself, but that check never ran: the traversal happened while the URL was being built, so the request reached a different endpoint and the file-path validator was never consulted.

  A whole segment equal to `.` or `..` is now refused by the files helpers, the pipe path builders in both the Node and browser entry points, the exec base-path assertion, and the agent client. The check runs after percent-decoding, since `%2e%2e` normalizes identically. Names that merely contain dots are untouched, so `.env`, `a.b` and `..hidden` still work. The exec assertion already refused `..` but accepted a bare `.`, which URL normalization removes, retargeting the request the same way.

- **Tunnel streams opened on a secondary WebSocket are handled.** A v2 session opens more than one socket and the kit may deliver a stream-open frame on any of them. The handler was attached to the first socket only, so those streams were dropped silently.

- **`hoody ai-fix` resolves its own defaults.** The built-in Hoody AI gateway authorizes by network position rather than by key, so the profile runs without one, and the resolver's missing-key rule then rejected the exact configuration the shipped CLI uses.

- **An agent turn no longer fails on a deployment with response signing disabled.** The client mints a container claim for parity with the other kits, and a deployment answering `503 SIGNING_NOT_CONFIGURED` made that mint fatal. It is best-effort now, and the turn proceeds on the container URL, which is what the agent kit authorizes on in any case.

### Changed

- **The supported Node versions move to 22.23.0 and 24.18.0.** The package declared `>=22.19.0`; it now declares `>=22.23.0 <23 || >=24.18.0`, so an older runtime is refused at install. Those two are the first releases on their respective lines to bundle a patched undici, and the tunnel client runs on Node's built-in WebSocket, which is where earlier releases are exposed to CVE-2026-12151. The field constrains Node only: Bun and the browser build are unchanged, and the browser build has no runtime requirement of its own.

- **The events subscribe payload drops four fields the server never read.** `action`, `event_types`, `resource_id` and `resource_type` are gone from the exported type. The action is the Socket.IO event name rather than a field, so a subscribe is `socket.emit('subscribe', payload)`; and subscribing joins a delivery room rather than selecting event types. The server broadcasts every type to the rooms a connection holds, so filtering by type belongs on the client, which is what the per-type handlers on `EventsClient` already do. Anyone who hand-rolled a subscribe from the exported type was sending names the server ignores, and got silence with no error.

  The rename belongs to the proxy rather than to this SDK. Its service table lists the service as `egress`, and the `proxy` and `p` aliases it used to accept are gone, so a hostname carrying the old segment does not route to the egress proxy at all. The SDK's catalog had not followed: `getKitCatalogEntries()` returned a slug of `proxy` and a `-proxy.` URL sample, so anything built from that entry pointed at a name nothing answers to. It returns the `egress` segment now.

  Only the service segment moves. The project and container IDs and the server are unchanged, so a stored URL can be repaired by replacing that one label.

- **Hoody AI's built-in defaults point at `ai.hoody.com` and the free model.** The endpoint default was `ai.hoody.com`, and the model default was a paid catalog id that an account with no AI credit is refused outright.

- **Breaking — resolving an app moved from `/api/v1/run/run` to `/api/v1/run/resolve`.** Both methods were renamed with it: `app.execution.runAppPost` is now `run.resolve` and `app.execution.runAppGet` is now `run.resolveGet`. `GET` still takes the selector as query parameters and `POST` still takes the full selector as a JSON body; both return the exact shell command to run. The response no longer carries the `terminal` and `terminal_request_preview` fields, so the two types that described them — `TerminalExecuteResponse` and `TerminalRequestPreview` — are gone. Nothing else about the call changed.

- **`hoody chat` needs no API key any more.** It previously required a configured AI provider and refused to start without one, running the model itself. It now asks Hoody's documentation assistant: you ask, the service answers, and the CLI renders it. There is no model, provider, token or temperature setting left to configure, and answers arrive with links to the documentation pages they came from. `--private` still disables every disk read and write for the process, and a non-default service origin is still refused unless you accept it explicitly with `--accept-endpoint`. The service caps a question at 2000 characters and a conversation at 20 turns.

### Added

- **Manage the agent's MCP servers over HTTP.** Nine methods under `agent.mcp` cover the whole lifecycle: `listMCPServers` returns the effective merged configuration for a live session together with each server's live state — connected or not, negotiated protocol revision, tool count, why it was revoked, recent stderr — and reports credentials as key *names* only, never values. `upsertMCPServer` and `deleteMCPServer` write one entry, `setMCPServerEnabled` flips a single `enabled` flag so credentials survive a disable, and `reconnectMCP` re-reads the settings layers and reconciles every live session.

  Every write is nonce-guarded: `beginMCPWrite` mints a single-use nonce bound to `{session, operation, resolved path}` and returns the current config hash, which you pass back as `expect_hash` so a concurrent edit is reported as a conflict instead of being silently overwritten. A nonce minted for a different operation fails closed. `parseMCPImport` previews what an import would write without touching a file and strips credential values from the preview; `importMCPServers` then applies it, understanding the Hoody, Claude/Cursor and VS Code dialects — a document mixing more than one is refused rather than guessed at, and validation is whole-batch so one bad entry aborts the import. `probeMCPServer` connects to a candidate config, reports the tools it advertises, and tears the connection down; because probing starts a process or makes an outbound request to a caller-chosen URL, it is human-only and refuses a machine caller with `403 human_only`.

  The same nine arrive in the CLI as `hoody agent mcp list · upsert · delete · set-enabled · probe · reconnect · import · parse · begin-write`.

- **Sign out of GitHub, and switch between linked accounts.** `agent.github.githubLogout` forgets a linked account and deletes the token copies an interactive clone left in checkouts the daemon can currently reach. That purge is best-effort by construction — a repository in a stopped container keeps its copy — so the reply carries `credential_purge: "partial"` and says to revoke the token on GitHub for a complete removal. `agent.github.githubSetActiveAccount` points every subsequent GitHub operation at an already-linked account, keyed by the `accounts[].key` (`<host>/<login>`) from `githubAuthStatus`. Adding a token already activates the account it belongs to; switching between accounts that both already exist is what this route is for.

- **Arm a BYOA agent backend and pin its model.** `agent.settings.setACPEnabled` enables or disables an ACP backend for delegated sessions — a delegated session is refused while its backend is disabled, so this is the prerequisite for delegated sessions on a host configured over HTTP. `agent.settings.setACPAgentModel` sets the default model and reasoning effort that backend connects with; a delegated session started without an explicit model inherits them, and an empty value clears the pin and returns the backend to its own default. Both answer `404 unknown_agent` for anything that is not a known backend.

- **Turn hardware virtualisation on for a container.** `api.containers.setContainerKvm` enables or disables `/dev/kvm` passthrough, so a container can run full virtual machines. It is available on rented and dedicated servers only, never on free-tier ones, and the container must be stopped. Send `kvm: true` or `kvm: false` (`dev_kvm` is accepted as an alias). The CLI spells it `hoody containers kvm`.

## [1.0.0-beta.9] — 2026-07-30

### Added

- **Order machines that aren't in stock.** Four new methods cover the whole flow: `listServerOffers` lists what can be built to order — hardware, location, price per rental length, one-time setup fee and remaining stock — and `reserveServerOffer` places the order. `listMyReservations` and `getMyReservation` follow it from `pending` to `fulfilled`, or `refunded` if the order was reversed before a machine was delivered. An offer is told apart from an in-stock machine by `delivery_hours`: anything available now reports `0`, an offer reports `1`–`720`.

  Reserving **charges immediately**, so the request is built to survive a retry. `idempotency_key` is required, and replaying one returns the original reservation instead of buying a second machine; `max_charge_cents` caps the total debit and is required whenever a setup fee applies. Each way the call can refuse has its own code — the offer was withdrawn, it sold out, the key was reused for different terms, the setup fee was not confirmed, or the total exceeded your ceiling — so a client can tell "nothing was charged" from "something went wrong".

- **Snapshot counts and caps.** Listing a container's snapshots now also reports `snapshot_count` and `max_snapshots`, so you can show how much room is left rather than discovering the cap by hitting it. Creating one past the cap fails with `CONTAINER_SNAPSHOT_LIMIT`, which carries the container, the current count and the limit.

### Changed

- **Renting a server can now carry a one-time setup fee, and the rent call documents how that fails.** `serverRental.rent` accepts `max_charge_cents`, a ceiling on the *total* debit — rent plus the one-time fee. It is **required whenever the server has a non-zero `setup_fee_cents`**, so a client that rents such a server without it is refused with `SETUP_FEE_CONFIRMATION_REQUIRED` rather than being charged a total it never confirmed. It is a ceiling, not an exact match, so a price *drop* still succeeds; if the live total is higher you get `CHARGE_EXCEEDS_MAX` and nothing is charged. Read the figure to confirm from `pricing.price_tiers[rental_days].total_first_payment`.

  The endpoint previously documented only its success response. It now documents the ways it can fail — `INSUFFICIENT_BALANCE` (with the shortfall broken down), `INVALID_DURATION`, `NO_PRICING`, `SERVER_UNAVAILABLE`, `SETUP_FEE_CONFIRMATION_REQUIRED`, `CHARGE_EXCEEDS_MAX` and `PRICING_INVALID` — so these are generated into the client instead of arriving as an untyped error. The available-servers listing gained `pricing.setup_fee`, `pricing.setup_fee_cents` and `price_tiers.*.total_first_payment`, and reports `delivery_hours` — `0` for anything in stock. Servers and rentals now report `setup_fee_cents` and `total_paid_cents`, so what was actually paid is visible after the fact.

- **Listing invoices can be paged, sorted and filtered.** `listUserInvoices` gained `page` and `filter` alongside the existing `limit`, `sort_by` and `sort_order`. `filter` takes a JSON object string over the sortable fields — `{"status":"paid"}` or `{"amount":{"gte":10}}` — with `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `like` and `in`; an unknown field or operator is rejected with `400` rather than silently ignored. `limit` is now documented as capped at 100 (default 20), and `sort_by` lists the fields it accepts, falling back to `created_at` for anything else.

- **Creating a snapshot documents the rest of its failure surface.** Alongside the cap, the call can now report that another snapshot operation is already running for the container, that the container is still being claimed (both `409`), or that its snapshot list could not be read so the limit could not be checked (`503`, also on the alias endpoints). Each refuses without creating anything.

- **`redirect_uri` is now required when starting GitHub or Google sign-in.** Both documented it as optional. Google's description now also states it must be on an allowed domain, which GitHub's already did.
- **PKCE `code_challenge` is pinned to its real shape.** `authorize`, `device/code` and `launch/initiate` all documented 43–128 characters, but a base64url-encoded SHA-256 digest is always exactly 43. The schema now says so, rejecting a malformed challenge before it leaves the client.
- **Snapshot `expiry` is a whole number of days, from 1 to 3650.** It was an unbounded number, so `0.5`, `-3` and absurdly distant dates all looked acceptable. Values outside the range are now rejected before the snapshot is created.

### Fixed

- **The GitHub and Google callbacks now describe a declined sign-in.** When someone cancels at the provider, the callback receives `error`, `error_description` and `error_uri` and no `code`. Both were documented as though `code` always arrived, so a generated client treated an ordinary cancellation as a malformed response.

## [1.0.0-beta.8] — 2026-07-27

### Added

- **`ramdisk_scope` on container create and update.** `container` (the default) keeps `/ramdisk` private to that container; `project` additionally mounts `/ramdisk/project`, shared with your other containers in the same project **on the same server** — a RAM disk is memory on one machine, so it cannot span servers. It is refused when the project has other members.
- **Ramdisk figures in container stats.** A new `ramdisk` block reports the sharing scope, the shared pool ceiling, whether any of that ceiling is held for you (`capacity_reserved`, always `false` — the pool is first-come, first-served, so it is not a denominator for a usage bar), and measured bytes per scope. The container **list** endpoint never measures, so its `usage` is `null` — that means "not measured", not "empty".
- **`invite_code` on GitHub and Google sign-in.** Both provider redirects now accept the invite code from a signup link, so a coupon captured by your own signup page survives the round trip to the provider and applies to the new account. Only a hash of the code travels in the OAuth state.

### Fixed

- **`hoody exec` wrote where the SDK does not read.** Commands in namespaces that take no explicit instance id resolved to service index `0`, while the SDK uses `1`. For `exec` that index *is* the namespace, so a script written through the CLI landed under `default/0/` and was invisible to the matching SDK call. Every namespace now defaults to `1`; an explicit `--…-id` still wins.
- **`hoody shell -- <command>` ran inside your interactive terminal.** One-shot commands now get a session of their own instead of executing in terminal 1 and inheriting its state.
- **`--terminal-id` was silently ignored.** The id was sent as a query parameter that the container gateway overwrites, so every session landed on terminal 1 regardless. It now travels where it takes effect: `--terminal-id 3` attaches to terminal 3. The same fix applies to the SDK's terminal helpers — SSH, local, desktop, and remote command execution — where a `terminal_id` option was dropped the same way, and to the connect URL returned after creating a session, which pointed at a fresh ephemeral terminal instead of the session just created.
- **Agent event streams resolved a different address than every other agent command** — index `0` instead of the singleton the rest of the CLI uses.

### Changed

- **`ramdisk` is now described accurately.** It read as a private allocation of up to half the host's memory that persisted across container reboots. In fact `/ramdisk` draws on a shared per-server pool — 512 MiB by default, never more than half the server's memory, shared with your other containers on that server — and its contents are **lost on a host reboot**, which is what makes it suitable for secrets and scratch data that must not reach disk. It counts against memory, not disk.
- Reference documentation regenerated for this release.
